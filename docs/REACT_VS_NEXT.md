# React vs Next.js — 척척발표 프론트 선택 가이드

> 팀 공유용. “Next면 백엔드도 처리 가능”뿐 아니라 **전체 비교** 후, 우리 구조 기준으로 결론을 내린다.  
> 근거: [`DEV_POLICY.md`](./DEV_POLICY.md) · [`API_SDK_TEMPLATE.md`](./API_SDK_TEMPLATE.md) · 현재 `chuckchuck` 모듈.

**결론 한 줄:**  
제품(연습·리허설·코칭) 앱은 **React + Vite SPA**.  
Next는 **마케팅/SEO/인증 사이트**가 필요할 때 별도로.  
Next API에 AI 모듈(F-01/F-05/F-06)을 넣는 구성은 **우리 정책과 맞지 않음**.

---

## 0. 먼저 용어 정리

| 말 | 뜻 |
|----|-----|
| **React** | UI 라이브러리. 보통 **Vite 등으로 SPA**를 만든다. |
| **Next.js** | React **프레임워크**. 라우팅·SSR/SSG·API Route·배포 관례가 포함됨. |
| 비교 대상 | “React만” vs “Next”가 아니라 **`React SPA(Vite)` vs `Next 앱`**. |

Next를 써도 화면은 React다. 차이는 **앱을 어디에 두고, 서버 렌더/서버 코드를 얼마나 쓰느냐**다.

---

## 0-1. 반박 대응: “분리 구조니까 오히려 Next가 좋다”

팀에서 자주 나오는 뒤집기 논리:

> “화면 / 서버 / 모듈을 나누는 구조잖아. 그럼 Next가 BFF·라우팅·미들웨어로 분리를 더 잘 받쳐 주지 않냐?”

**결론: 그 논리의 전제가 반대입니다. 분리가 확실할수록 SPA가 더 맞습니다.**

### 왜 “분리 → Next”가 성립하지 않는가

| 분리의 의미 (우리) | Next가 잘하는 것 | 관계 |
|--------------------|------------------|------|
| 화면은 UI만, AI는 Python 모듈 | 화면 레포 안에 서버 코드도 두기 | **충돌** — Next는 경계를 두껍게 만들기 |
| `ours` JSON으로만 교환 | Server Actions / Route Handler에 로직 두기 | **유혹** — 계약 밖으로 새기 쉬움 |
| 모듈 담당 · 화면 담당 분리 소유 | 한 프레임워크에 FE+BFF 밀착 | **소유권 혼선** |
| 이미 독립 API (`/api/v1/*`) | rewrite·proxy로 API 감싸기 | proxy는 **Vite/nginx로도 됨** — Next 이유 아님 |

정리하면:

1. **백엔드가 이미 분리되어 있다** = 프론트는 “호출만 하는 클라이언트”면 충분하다.  
2. Next의 강점(SSR, API Route, RSC)은 **프론트 프레임워크가 서버 역할도 가져갈 때** 빛난다.  
3. 우리가 서버 역할을 **의도적으로 안 가져가기로** 했다면, Next의 핵심 강점을 **쓰지 않은 채** 복잡도만 가져오는 셈이다.  
4. “분리된 API에 붙는 웹앱”의 교과서 조합은 **`SPA + REST/JSON API`** 이다. (관리자, Figma류 도구, 대시보드가 이 패턴)

### “BFF가 필요하면 Next 아니냐”

얇은 BFF(인증 쿠키, CORS, `/api` 프록시)가 필요하면:

| 수단 | 역할 | Next 필수? |
|------|------|------------|
| Vite `server.proxy` (로컬) | 개발 중 CORS 회피 | ❌ |
| nginx / API Gateway / Cloudflare | 배포 프록시 | ❌ |
| Python FastAPI에 세션·CORS | 서버가 이미 있음 | ❌ |
| Next rewrite / Route Handler | 동일 역할 가능 | **선택지일 뿐** |

BFF가 필요해도 **그게 Next를 고르는 이유가 되진 않습니다.**  
“프록시 한 줄” 때문에 App Router·RSC·서버/클라 경계를 전부 비용이 큽니다.

### 한 문장으로 되받아치기 (복붙)

> 분리되어 있어서 Next가 좋은 게 아니라, **분리가 잘 돼 있어서 Next의 서버 기능이 필요 없는 거**예요.  
> Next는 ‘프론트와 서버를 한 프레임워크로 묶을 때’ 이득이 크고,  
> 우리는 일부러 안 묶는 구조라서 **얇은 React SPA가 분리에 더 잘 맞습니다.**

### 그림으로

```
❌ 분리 구조 + Next를 “풀로” 쓰는 착각
[Next 화면 + Next API/BFF + (또) Python AI]
        ↑ 서버가 두 층 — 분리가 아니라 중간층 추가

✅ 우리 정책과 맞는 분리
[React SPA] ──ours──► [Python API / 모듈] ──► [외부 AI]
        ↑ 경계 1개, 계약 1개
```

상대가 “분리를 Next가 더 잘 지원한다”고 하면, 이렇게 되물으면 됩니다:

1. Next로 **무엇을** 분리한다는 거지? (화면↔AI는 이미 분리됨)  
2. Next 서버에 **어떤 로직**을 둘 생각이지? (오케스트레이션만? AI?)  
3. 그 로직이 Python에 있으면 안 되는 이유가 있나?  
4. proxy/인증만 필요하면 왜 **프레임워크 전체**가 필요하나?

답이 “편의 / 익숙함 / SEO”면 인정 가능 범위고,  
답이 “분리라서”면 **인과가 뒤바뀐 것**이라고 보면 됩니다.

## 1. 전체 비교표 (일반)

| 관점 | React + Vite (SPA) | Next.js | 우리 제품에 유리한 쪽 |
|------|--------------------|---------|----------------------|
| **정체** | 클라이언트 앱 | 풀스택에 가까운 프레임워크 | SPA — 백엔드는 이미 Python |
| **렌더링** | CSR 기본 | SSR / SSG / RSC / CSR 혼합 | CSR — 로그인 후 앱, SEO 불필요 |
| **라우팅** | React Router 등 직접 | 파일 기반 내장 | 둘 다 OK, SPA로 충분 |
| **SEO** | 약함 (CSR) | 강함 (SSR/SSG) | 랜딩만 필요 → 제품 앱엔 무관 |
| **초기 로딩** | JS 번들 후 화면 | HTML 먼저 가능 | 앱은 “사용 중”이 핵심, 랜딩만 Next 이득 |
| **백엔드 코드** | 없음 (API 호출만) | API Route / Server Actions | **넣지 않는 게 정책** — Python이 서버 |
| **학습·복잡도** | React + 빌드툴 | React + Next 규칙(RSC, 캐시, 경계) | 팀 규모·일정상 SPA가 단순 |
| **배포** | 정적 호스팅 + API 분리 | Vercel 등과 궁합, 또는 Node 서버 | API는 Python 고정 → SPA+API 분리 자연 |
| **실시간·브라우저 API** | 제약 적음 | Client Component로 가능하나 경계 관리 필요 | **녹음/PDF = SPA가 단순** |
| **타입·생태계** | React  эко | 동일 + Next 전용 패턴 | 동등 |
| **테스트** | 컴포넌트/E2E 단순 | 서버/클라이언트 경계 테스트 추가 | SPA가 단순 |
| **이직·채용** | React 경험자 다수 | Next 경험도 흔함 | 동등~Next 약간 유리 |
| **잠금(lock-in)** | 낮음 | 프레임워크·배포 관례에 묶이기 쉬움 | 모듈 독립 정책상 **잠금 낮을수록 유리** |

### Next가 일반적으로 이기는 경우

- 공개 웹(랜딩, 블로그, 문서) **SEO**
- 첫 페인트·공유 미리보기가 중요
- **하나의 TS 레포**에 웹+얇은 BFF를 빠르게
- 쿠키 세션·미들웨어로 인증 게이트

### React SPA가 일반적으로 이기는 경우

- **로그인 후 도구형 앱** (대시보드, 에디터, 녹음기)
- 백엔드가 **이미 별도** (Python/Java/Go…)
- 마이크·카메라·WebSocket·캔버스 등 **브라우저 중심**
- 팀이 **화면 / API 모듈**을 나눠 소유

→ 척척발표 본제품은 아래 표의 **후자**에 가깝다.

## 3. 아키텍처·정책 관점 (우리 고유)

### 3-1. 정해 둔 계층

| 계층 | 하는 일 | 하지 않는 일 |
|------|---------|--------------|
| **화면** | 업로드·표시, 녹음·슬라이드 시각 | 모듈 내부 로직·벤더 raw |
| **서버** | 오케스트레이션, 저장, API 창구 | 모듈끼리 직접 연결 |
| **기능 모듈** | 자기 F-ID만 | 다른 모듈 import, raw 유출 |

```
화면 / JS SDK
    →  ours JSON
서버  POST /api/v1/{action}
    →  기능 모듈 fXX_*.py
    →  providers (raw는 여기만)
```

Next는 이 그림에서 **화면**(± 얇은 프록시) 자리.  
가운데·아래는 **Python `chuckchuck` 유지**.

### 3-2. “Next면 백엔드 일부 가능”에 대한 답

| 주장 | 답 |
|------|-----|
| 프론트 레포에서 백엔드 처리 가능 | **가능 ≠ 우리 구조에 맞음.** F-01/05/06이 Next에 섞이면 계층 붕괴 |
| BFF 하나면 편하다 | BFF = 인증·프록시·오케스트레이션만. AI 본체는 이미 Python |
| React만 쓰면 서버가 없다 | 서버는 **이미 있음**. SPA는 그걸 호출 |
| 나중에 맞추면 된다 | 지금 Next에 로직 넣으면 **이중 백엔드·이전 비용** |

### 3-3. Next API에 AI를 넣을 때 실무 리스크

1. **이중 백엔드** — 배포·로그·타임아웃·에러 포맷 2곳  
2. **시크릿·과금** — Upstage/A.X/Solar 키가 프론트 배포와 묶임  
3. **장시간 작업** — PDF 파싱·STT·52장 개념 배치 vs 서버리스 제한  
4. **`ours` 계약 훼손** — `contracts.py` 말고 ad-hoc JSON 증가  
5. **소유권 혼선** — 모듈 담당 / 화면 담당 PR이 한 레포에 엉킴

## 5. 비용·배포·운영

| 항목 | React SPA | Next |
|------|-----------|------|
| 프론트 호스팅 | S3/CloudFront, Netlify, Cloudflare Pages 등 정적 | Node 런타임 또는 Vercel |
| API | Python 서버/컨테이너 별도 (기존) | 동일 + (실수 시) Next API 추가 비용 |
| 스케일 | 정적 CDN + API 스케일 분리 | 풀스택을 한곳에서 키우기 쉬움 → **우리엔 분리가 맞음** |
| 장애 분리 | 화면 CDN 살아 있어도 API만 점검 가능 | 한 레포 장애 범위가 커지기 쉬움 |

AI 워크로드(파싱/STT/LLM)는 **CPU·타임아웃·키 관리**가 프론트와 성격이 다름 → **처음부터 분리**가 운영에 유리.

## 8. 자주 나오는 오해

| 오해 | 정정 |
|------|------|
| React는 구식, Next가 현대적 | Next는 **다른 문제**(풀스택·SEO)용. 도구형 SaaS는 SPA가 여전히 표준 |
| Next 써야 React 18/19를 씀 | Vite SPA도 동일 React |
| SPA는 SEO 때문에 무조건 손해 | **제품 앱**은 검색 노출 대상이 아님. 랜딩만 분리 |
| Next API = 우리 서버 대체 | 우린 이미 서버·계약·프로바이더가 있음. 대체 아니라 **중복** |
| **분리 구조니까 Next** | **반대.** 백엔드가 이미 분리됐으면 프론트는 얇은 SPA면 됨. Next는 오히려 중간 서버 층을 추가하기 쉬움 |
| 나중에 바꾸면 된다 | 서버 로직을 Next에 넣는 순간 이전이 비싸짐. **처음부터 경계**를 지키자 |

## 9. 회의 스크립트 (2분)

1. **전체 비교:** Next는 SEO·풀스택에 강하고, SPA는 별도 API + 브라우저 앱에 강하다.  
2. **우리 제품:** 녹음·marks·PDF·코칭 = SEO 불필요, 브라우저 중심.  
3. **우리 정책:** 화면 ≠ 기능 모듈. AI는 Python `chuckchuck`.  
4. **“분리니까 Next”:** 인과가 반대. 분리돼 있어서 **Next 서버 기능이 필요 없음**. SPA가 분리의 정석.  
5. **“백엔드 일부”:** 가능하지만 이중 백엔드·계약 훼손·장시간 작업 리스크.  
6. **결정:** 제품 = **React + Vite**. Next = **랜딩/인증이 필요할 때 별도**.

## 10. 결정 문장 (복붙용)

> React vs Next를 일반론으로만 보면 Next가 더 많은 걸 제공합니다.  
> 다만 우리 제품은 SEO가 아니라 **브라우저 리허설 도구**이고, AI 백엔드는 **이미 Python 모듈**로 분리돼 있습니다.  
> “분리 구조라서 Next”는 인과가 반대예요. 분리가 확실할수록 프론트는 얇은 SPA면 되고, Next의 서버 강점은 안 쓰게 됩니다.  
> Next API에 백엔드를 일부 넣는 건 가능하지만 중간 층이 늘고 cascade 정책과 충돌합니다.  
> 그래서 제품 프론트는 **React + Vite SPA**, Next는 **마케팅/인증이 필요할 때** 쓰자고 제안합니다.
