## 결론: 바꾸지 않는다

**Solar 유지.** 속도만 보면 믿:음이 31배 빠르지만, 산출물이 다른 물건이다.

- 같은 12장에서 **Solar 20노드/64간선 vs 믿:음 5노드/5간선**
- 믿:음은 깊이가 2단까지만 나온다 — 위계가 사실상 없다
- F-11 정합 판정은 이 노드들을 판정 대상으로 쓴다. 노드가 5개면 **발표의 4분의 3이 아예 평가 대상에서 빠진다**. 빨라진 게 아니라 일을 덜 한 것이다

## 실패한 둘

**A.X** — 게이트웨이가 500 을 냈다. 우리 타임아웃(연결 10초/응답 30분)이 아니라 A.X 쪽 업스트림이 먼저 끊겼다:

```
axllm: do request: context deadline exceeded (Client.Timeout exceeded ...)
```

우리가 고칠 수 있는 문제가 아니다. STT 용으로는 A.X 를 계속 쓰지만 추론 백엔드로는 후보에서 뺀다.

**EXAONE** — 두 번 다 `max_tokens=8192` 를 꽉 채우고도 JSON 을 못 끝냈다. 응답이 이렇게 시작한다:

```
"Okay, let's tackle this problem. So, I need to ..."
```

사고 과정을 그대로 뱉는 모델이라 "JSON 만 출력하라"는 지시를 안 지킨다. 8192 토큰을 두 번 = 470초를 태우고 실패했다. 쓰려면 프롬프트가 아니라 **응답에서 JSON 만 뽑아내는 어댑터**가 필요하다 — F-07 만의 문제가 아니라 모든 단계에 걸린다.


## 추가 검증: "믿:음을 잘 쓰면 되지 않나"

데모용으로 4초짜리 믿:음을 쓰자는 제안이 나와, 5노드가 모델 한계인지
프롬프트가 요구를 안 한 탓인지 확인했다.

**1차(n=1): 커버리지 지시를 붙이니 13노드/25간선이 나왔다.** 프롬프트 문제로 보였다.

**반복해 보니 이상치였다.** 같은 조건 6회:

```
노드  5, 5, 7, 6, 7, 5      평균 5.8
최대깊이  2, 2, 2, 2, 2, 2   ← 한 번도 3단이 안 나온다
```

13은 재현되지 않았다. **믿:음은 이 작업에서 5~7노드·2단이 실력이다.**
프롬프트 위치도 바꿔 봤지만(유저 → 시스템) 달라지지 않았다.

### 그리고 그 시도가 Solar 를 깎았다

커버리지 문구를 넣은 뒤 Solar 간선 수가 이렇게 움직였다:

| 프롬프트 | Solar 간선 |
|---|---|
| 수정 전 | **64** |
| 유저에 추가 | 40 |
| 시스템에 추가 | 35 |

`"노드 하나당 평균 2개 이상 연결된다"` 를 **하한**으로 썼는데 20노드 × 2 = 40 —
모델이 **목표치**로 받은 정황이다. 믿:음은 안 고쳐지고 Solar 만 깎였으므로 **되돌렸다.**

교훈 둘:
- **n=1 로 결론을 뒤집지 마라.** 3초짜리 호출은 6번 돌려도 20초다.
- **하한을 적으면 상한으로 읽힌다.** 숫자를 주려면 왜 그 숫자인지까지 적어야 한다.

## 곁가지: 느린 건 작업이 아니라 서버다

같은 F-06 호출의 생성 속도가 실행마다 이렇게 흔들렸다:

```
99.3 tok/s  →  9.8 tok/s      (같은 프롬프트, 몇 분 간격)
```

**10배 편차.** F-07 이 160초 ↔ 442초로 흔들린 것도 같은 원인이다. 출력은 678~2,714 토큰으로 작고 호출도 1번뿐이다 — 프롬프트를 줄이거나 작업을 쪼개는 최적화는 의미가 없다. 병목이 우리 쪽에 없다.

그래서 응답 타임아웃을 30분으로 두고(연결은 10초), 호출마다 `[llm] name/model 초 in=N out=N (tok/s)` 를 남긴다. 다음에 느릴 때는 추측하지 말고 로그를 본다.

## 남은 실험 하나

`MAX_TOKENS=8192` 인데 Solar 실제 출력은 2,714 토큰이다. 3배 과다 예약이라, 일부 추론 서버는 이 값으로 스케줄링을 판단한다. **4096 으로 낮춰 지연이 줄어드는지** 볼 값어치가 있다 — 다만 큰 덱에서 잘릴 위험이 있어 실측 비교가 먼저다.
