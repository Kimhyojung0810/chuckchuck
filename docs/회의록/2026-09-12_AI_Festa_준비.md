## 4. Q&A 개발 방식 자체를 바꿀 필요

### 문제

프롬프트·모델을 고칠 때마다 PPT/발화를 넣고 생성 질문을 **사람이 하나씩 읽어** 확인한다. 파인튜닝까지 가면 버전이 더 늘어나서 이 방식으로는 속도가 안 난다.

### 방향: Q&A Benchmark + Automated Evaluation Pipeline

- 고정된 발표/발화 테스트 세트를 만들어, 버전이 바뀔 때마다 **같은 조건으로 반복 평가**.
- 문장 exact match 가 아니라 **의미·역할 기준 rubric** 으로 채점.

| 항목 | 묻는 것 |
|---|---|
| Groundedness | PPT/발화에 근거하는가 |
| Relevance | 실제 발표와 관련 있는가 |
| Coverage | 중요한 설명 부족·빈틈을 짚는가 |
| Depth | 단순 사실 확인에 그치지 않는가 |
| Answerability | 자료·발화 맥락으로 답할 수 있는가 |
| Non-duplication | 질문끼리 중복되지 않는가 |
| Fatal Error / Hallucination | 자료에 없는 내용을 전제로 묻는가 |

- 초반엔 사람이 일부 케이스를 채점해 기준을 맞추고, 이후 **LLM-as-a-Judge** 로 대부분 자동화.
- 버전마다 batch test 를 돌려 **이전 버전 대비 regression report** 가 바로 나오게 한다.

### Test Set 은 학습 데이터와 분리

- 개발 중 계속 보는 **Eval Set** 과, 끝까지 숨겨 두는 **Holdout Test Set** 을 분리.
- 파인튜닝을 하더라도 최종 benchmark 데이터는 학습에 넣지 않는다. 안 그러면 숫자만 좋아지는 overfitting.

### 저장소에 이미 있는 것 (여기서 출발한다)

| 있는 것 | 무엇을 하나 | 벤치마크로 가려면 |
|---|---|---|
| `examples/qa_eval.py` | 근거 인용률·질문 특이도·폴백 비율·판정 일관성·말투 위반을 재고 `--tag` 로 결과 파일에 꼬리표 | 위 7개 rubric 을 LLM-judge 항목으로 추가, 두 `--tag` 결과를 나란히 비교하는 report 출력 |
| `examples/build_eval_bundle.py` → `exports/eval_bundles/*.json` | 학습 동의한 실제 세션을 평가 묶음으로 변환. `qa_eval.py --bundle-dir` 가 N건 평균±편차를 찍는다 | 고정 Eval Set 후보. 동의 세션만 쓴다 ([PRIVACY.md](../PRIVACY.md)) |
| `examples/replay_sessions.py --stage questions` | 프롬프트를 고친 뒤 "그때 vs 지금" diff | regression report 의 질적 근거 |
| [RUBRIC_SCORING_PLAN.md](../RUBRIC_SCORING_PLAN.md) | 발표 평가(채점표 v3) 쪽 rubric | Q&A rubric 과 용어를 맞춘다 |

## 5. 결선까지 Q&A 성능 개선 스토리를 단계적으로 쌓기

> 📈 결선에서 보여줄 것은 "좋은 모델 하나" 가 아니라, **같은 기준으로 5~6번 반복 평가하며 개선했고 마지막에 실제 사용자로 검증했다** 는 흐름.

1. **Baseline 구축** — 현재 Q&A 모델/프롬프트를 고정 benchmark 로 최초 평가
2. **Prompt / Rubric 개선** — 질문 생성 기준, grounding, 중복 방지
3. **Context / Data 개선** — PPT 핵심 추출, transcript 처리, few-shot/RAG/context 구성
4. **Fine-tuning 실험** — 데이터 확보·라벨링 후 SFT/LoRA. **반드시 prompt baseline 과 같은 benchmark 로 비교**
5. **AI Festa Human Test** — 10/6~10/8 실제 관람객 체험. 만족도·유용성·받을 법한 질문인지·오류/무관 질문 수집
6. **Final Validation** — Festa 피드백 반영 후 holdout test + 사람 평가

- 최종 발표에서 `Baseline → Prompt → Context → Fine-tuning → Festa 반영` 순으로 benchmark 가 올라가는 그래프를 내야 한다. **개발 과정부터 수치를 남긴다** (매 단계 `qa_eval.py --tag <단계>` 결과 파일을 보관).
- Benchmark 는 **시스템적으로 좋아졌는가**, Human Test 는 **사람이 실제로 유용하다고 느끼는가** 를 각각 입증한다.

## 6. 데이터셋 기반 Fine-tuning

- 가설: **데이터셋을 확보하고 파인튜닝까지 하는 팀은 많지 않을 것** → 정량 개선까지 보이면 결선의 기술적 차별점.
- 단, "파인튜닝을 했다" 가 목적이 아니다. **일반 LLM + Prompt 보다 Q&A 품질이 실제로 좋아졌음을 benchmark 로 증명**하는 것이 목적.
- 참고: F-18 말버릇 LoRA 는 이미 AI Hub 라벨로 저장소 밖에서 학습한 전례가 있다 ([WORKLOG 2026-09-10](../WORKLOG.md)). Q&A 파인튜닝은 그와 별개로, 라벨 구조부터 새로 정해야 한다.

### 역할 분담

| 역할 | 담당 | 할 일 |
|---|---|---|
| 데이터셋 탐색/선정 | **종원, 선호** | 발표 평가 / Presentation / Speech Assessment / PPT-발화 비교 / Q&A / 교육용 rubric 공개 데이터셋 탐색. 규모·언어·label 구조·라이선스·활용 가능 여부 비교. **우리가 필요한 형태가 존재하는지 먼저 확인** |
| Fine-tuning 구현/검증 | **효정, 현석** | 전처리·학습 포맷 설계. 현재 모델에서 가능한 방식 검토 (SFT/LoRA 경량 우선). Prompt/Few-shot baseline 대비 성능 비교 |

### 데이터 확보 우선순위

1. 공개 데이터셋 최대한 활용
2. 기존 데모/발표 자료로 자체 데이터 생성·라벨링
3. 부족하면 **개발지원금으로 유료 학습용 데이터셋 구매** 검토
4. 외부 라벨링 업체 비용은 지원 항목에 없음 → 필요하면 **운영사무국에 사전 문의**

**먼저 정할 것 — 우리가 필요한 데이터 구조:**

```
slide/document → transcript → 핵심 개념 → 언급 여부/설명 충분도 → 예상 질문 → 피드백
```

원하는 데이터셋이 없으면 자체 labeling 기준을 만들어 구축하는 것까지 고려.

## 7. AI Festa 에서 Human Evaluation 확보

Festa 를 홍보 행사가 아니라 **결선 전에 실제 사람으로 검증하는 실험장**으로 쓴다. 결과보고서·결선에 쓸 수 있게 다음을 남긴다.

- 체험자 수
- Q&A 실제 사용/완료 횟수
- 질문 유용성 평가
- 실제 발표에서 받을 법한 질문인지
- 가장 유용했던 기능
- 무관/중복/이상 질문 발생 여부
- 전체 만족도 · 재사용 의향
- 자유 의견

`자동 benchmark 상승 + 실제 사용자 평가` 를 같이 내는 것이 가장 강한 입증 구조.

**구현 메모:** 질문 코칭에는 이미 👍/👎 · 「이 판정은 아닌 것 같아요」 버튼이 있고 학습 동의 세션에만 기록된다
([PRIVACY.md](../PRIVACY.md)). 부스에서는 동의 체크박스를 관람객에게 어떻게 설명·수집할지, 세션 수를 어떻게 셀지
(`var/data/sessions/YYYY/MM/DD/` 폴더 수) 를 8번 할 일에서 같이 정한다.
