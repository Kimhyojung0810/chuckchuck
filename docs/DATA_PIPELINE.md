# 척척발표 — 데이터 구성·수집·활용 방안

이 문서는 척척발표가 국내 AI 모델(KT 믿:음)을 파인튜닝하기 위해 **AI Hub 공적말하기
실습 및 평가 데이터**를 어떻게 구성·수집·가공·활용했는지 정리한다. 실험 원본은
`/home/ubuntu/workspace/20_AIHub_data`(이 프로젝트 밖, 읽기 전용 참조)에 있고,
그 결론 중 실서비스에 연결된 부분만 `00_chuckchuck/chuckchuck/`에 들어와 있다.
단일 원본은 `20_AIHub_data/README_FINETUNING.md`·`RESULTS_2ND.md`이며, 수치가
이 문서와 어긋나면 그쪽이 맞다. 요약은 [`docs/2026_AI_루키_본선_제안서_개발성과.md`](2026_AI_루키_본선_제안서_개발성과.md)
§3.1.4-사에도 있다.

## 1. 데이터 출처

**AI Hub「공적말하기 실습 및 평가 데이터」**(2023년 구축, NIA, 수행기관 ㈜유핏 외).

| 항목 | 값 |
|---|---|
| 수집 대상 | 중학생~50대 이상 800명, 발표 영상+메타데이터 |
| 언어적 원천/라벨 | 800건 (연령·성별·주제·난이도·발표환경별 분산 수집) |
| 비언어적 원천/라벨 | 288,000건 / 28,800건 (손동작·머리동작·자세 12종 제스처) — **이 프로젝트는 미사용** |
| 우리가 실제 확보한 것 | **Training 640건만.** Validation 라벨(`VL_1.언어적_*.zip`)은 AI Hub 로그인이 필요해 미다운로드 |
| 원천 오디오 96GB | **파손** — `.irx923`/`.irx939` 부분파일. 음성 질(voice_quality) 학습 불가 |

비언어적(제스처) 데이터를 안 쓰는 이유는 척척발표가 카메라 기반 자세 분석을 하지 않고
음성·전사문 기반으로만 동작하기 때문이다.

### 1-1. 라벨 스키마 (언어적, 우리가 쓰는 부분)

```
speaker         : age_flag(연령), gender, job, aud_flag(청중 규모)
presentation    : presen_topic, presen_type(설명/주장/찬반), presen_location,
                  presen_script(원고 전문), presen_difficulty(상/중/하)
script          : start_time/end_time, script_stt_txt(발화 STT),
                  script_tag_txt(태그 인라인 매핑), syllable_cnt, word_cnt, sent_cnt
taglist[]       : tag_id, tag_keyword(스팬 텍스트), tag_type(1=FIL 2=REP 3=PS 4=WR)
evaluations[40] : 발표당 평가자 40명(expert 10 + semi-expert 10 + person 20)
                  eval_grade(A+~F), repeat/filler_words/pause/wrong/voice_quality/
                  voice_speed 각 {cnt, scr(1~5점)}. person 20명은 등급만, 항목 점수는 null
```

이름 등 개인정보는 원본에서 이미 마스킹돼 있다 (예: `presen_script`의 "반\*문 총장").

## 2. 수집·가공 파이프라인

원본 라벨 zip을 그대로 학습에 쓰지 않고, 세 가지 실측 기반 변경을 거쳤다
(`20_AIHub_data/src/build_dataset.py`, `build_expert_rules.py`, `build_task_dataset.py`).

### 2-1. 원고 그룹 분할 (데이터 누수 방지)

640건은 고유 원고(`presen_script`) 296개를 여러 발표자가 나눠 읽은 것이라, 무작위 분할을
하면 같은 원고가 train/test 양쪽에 들어가 성능이 부풀려진다. **원고 SHA1 기준 그룹 분할**
(seed 42 고정)로 `train 513 / val 65 / test 62`를 구성했다. Validation 라벨을 못 받아
이 내부 분할이 유일한 held-out이므로 누수 차단이 특히 중요했다.

### 2-2. 학습 타깃을 인라인 태그 전문 → 스팬 목록으로 변경

원래 라벨엔 `script_tag_txt`(전문에 태그가 박힌 1,950자 텍스트)가 있지만, 이를 그대로
타깃으로 쓰면 학습 손실 대부분이 "원문 1,500자를 그대로 베끼는" 데 쓰인다. 대신 라벨에
함께 있던 `taglist`(태그·스팬 키워드 목록, 평균 331자)를 타깃으로 썼다 —
`taglist`와 인라인 태그의 일치율 97.7%, 스팬 키워드가 원문에 실제로 존재하는 비율 99.3%를
확인한 뒤 채택. `<PS/>`(휴지)는 본문에 앵커가 없어 스팬으로 예측이 불가능해 학습 대상에서
제외하고, 대신 음성인식 타임스탬프로 계산하기로 했다(§4-5).

### 2-3. 태그별 데이터셋 분리

REP(반복)·FIL(간투어)·WR(발음오류/이표현)를 통합 학습했더니 각 태그의 최적 디코딩 조건이
서로 배타적이라는 게 드러났다(§3-2). 그래서 태그별 별도 데이터셋(`data/tagging_{REP,FIL,WR}/`)
으로 다시 쪼갰다 — 타깃 길이가 통합 331자에서 REP 152 / FIL 76 / WR 102자로 줄었다.

## 3. 모델 학습·평가에 어떻게 썼는가

베이스 모델은 전 실험 공통으로 **`K-intelligence/Midm-2.0-Base-Instruct`(11.5B)**,
LoRA(r=16 α=32 dropout=0.05, q/k/v/o/gate/up/down), 시드 42/43/44 3개 반복 학습(단일
시드 수치는 신뢰 불가 — n=640이라 시드 분산이 실재함).

### 3-1. 반복 표현(REP) 태거 — 실서비스에 연결됨

zero-shot F1 0.010 → 파인튜닝 후 **0.686 ± 0.027**. 예측 676개/정답 702개로 카운트
캘리브레이션도 맞다. **무보정 greedy 디코딩으로 서빙해야 한다** — REP는 정의상 반복이라
`repetition_penalty`를 걸면 정답 생성 자체가 막힌다.

### 3-2. 간투어(FIL) 태거 — 통합 학습은 퇴행, 분리+앙상블로 개선

통합 학습에서는 파인튜닝(0.519)이 베이스 zero-shot(0.653)보다 나빴다 — 정밀도를 팔아
재현율을 산 트레이드였다. 원인은 긴 발화에서 greedy 디코딩이 같은 줄을 반복하는
**생성 붕괴**(62건 중 48건, 512토큰 상한 도달 44건)였다. `repetition_penalty=1.2` +
**3시드 앙상블(min 방식)**을 적용해 **정밀도 0.9927 / 재현율 0.7253 / F1 0.8382**까지
끌어올렸다(`data/tagging_FIL/ensemble_eval_rp1.2.json`). 단 REP와 정반대로 페널티가
필요해 **같은 추론 패스에서 REP와 같이 뽑을 수 없다** — 별도 패스가 필요하므로 아직
서비스에 연결하지 않았다.

### 3-3. 발음오류(WR) 태거 — 실패, 미사용

통합·분리 학습 모두 실패했다(F1 0.05~0.06, 붕괴 제거해도 천장 0.2). 전문가 채점 규칙
분석(§3-4)에서도 "발음은 전문가조차 카운트와 무관하게 점수를 준다"는 게 확인돼, 애초
텍스트만으로 학습 가능한 신호가 아니었다.

### 3-4. 전문가 채점 규칙 추출 (파인튜닝이 아니라 통계)

평가자 12,800행(expert+semi-expert)에서 카운트→점수 임계값을 역산했다
(`build_expert_rules.py`). 반복 5점≤4회, 간투어 5점≤12회, 긴쉼 0회=5점 등 항목별
결정성 66.9~87.0%를 확인. 등급을 6개 항목의 **선형회귀**로 예측했을 때 5특징
R²=0.86(RMSE 0.461 GPA)로, **11.5B 파인튜닝보다 파라미터 7개 회귀가 이미 이론 상한에
가까워** 등급 자체를 직접 파인튜닝할 근거가 없다고 판단했다.

### 3-5. 국내 LLM 4종 zero-shot 채점 벤치마크

Solar Pro3·A.X-K1·EXAONE·Mi:dm(로컬 베이스)에 전사문+맥락만 주고 전문가처럼 채점시켰다.
평균 MAE 1.41~1.58로 4개 모델이 뭉쳐 있어 — **모델 차이가 아니라 "zero-shot 채점" 자체가
이 태스크에 안 맞는다**는 결론을 얻었다(오라클 규칙 기준 MAE 0.330 대비 4~5배 나쁨).
이 실험 도중 KT 믿:음의 Friendli dedicated 엔드포인트가 HTTP 410으로 종료된 걸 발견해
로컬 서빙(`serve_midm.py`)으로 전환한 계기가 됐다.

### 3-6. 하이브리드 등급 모델 — 연구 성과의 최종 결론

항목별로 "텍스트에 정보가 있는가"를 기준으로 담당을 나눴다.

| 항목 | 담당 | 이유 |
|---|---|---|
| 반복·간투어 | 믿:음 LoRA 태거 | 전사문에 그대로 드러남 |
| 휴지·속도 | A.X STT 타임스탬프 | 침묵·속도는 텍스트에 없고 계산으로 나옴 |
| 발음 | 중앙값 | 어떤 방법으로도 학습 실패 |

원고 그룹 분할 held-out 62건에서 등급 정확 일치가 상수 기준선 9.7% → **51.6%**로
향상(GPA MAE 0.995→0.459), 사람 주석 카운트를 쓴 오라클 상한(50.0%)과 동급이었다.
±0.5 GPA 이내는 62.9%로, "발표 3건 중 2건은 전문가 한 명 수준으로 맞힌다"에 해당한다.

## 4. 실서비스(F-18)에는 무엇이 들어갔나

| 연구 산출물 | 서비스 연결 여부 |
|---|---|
| REP LoRA (무보정 greedy) | ✅ `HABIT_PROVIDER=lora`, `chuckchuck/_lora_tagger.py` |
| FIL·PAUSE | 규칙 기반(heuristic)으로 보강 — LoRA 미사용 |
| FIL 앙상블 태거(F1 0.838) | ❌ 별도 추론 패스가 필요해 미통합 |
| 전문가 채점 규칙·하이브리드 등급 모델 | ❌ 연구 인프라 단계 결과, F-14 채점표와 별도 |
| 국내 LLM 4종 zero-shot 채점 | ❌ 벤치마크용, 서비스 미사용(대신 F-12 청중 수다에 캐릭터로 활용) |

`REASONING_BACKEND=midm`으로 실행하면 위 로컬 서빙(`serve_midm.py`, GPU 21.5GB)이
그대로 붙는다 — `chuckchuck`의 `MidmLLM`이 이미 OpenAI 호환 클라이언트라 `.env` 세 줄
(`MIDM_BASE_URL`/`MIDM_ENDPOINT_ID`/`MIDM_API_KEY`)만 바꾸면 되고 서비스 코드는
고치지 않았다.

## 5. 2차 계획(`PLAN_2ND_FINETUNING.md`) 대비 실제 구현 현황

2026-08-11에 세운 2차 계획은 "12시간 안에 전문가 채점 지식을 서비스에 낸다"는 목표로
4단계를 잡았다. 실제로 코드를 확인한 결과는 다음과 같다.

| 단계 | 계획 | 산출물(계획) | 실제 구현 |
|---|---|---|---|
| 1단계 | 전문가 채점 엔진 이식 (카운트→1~5점 룩업 테이블, 등급 회귀를 서비스에 연결) | `chuckchuck/f21_expert_grade.py` | ❌ **미구현** — 해당 파일 없음 |
| 2단계 | 또래 비교 백분위 (연령×청중규모×발표유형별 분포로 "상위 N%" 산출) | `chuckchuck/f22_peer_norm.py`, `data/norms/percentile_table.json` | ❌ **미구현** — 둘 다 없음 |
| 3단계 | 태깅 확장 — REP/FIL/WR 태스크 분리 + 시드 3개 학습, 카운트 MAE 기준 평가 | `runs/{fil,wr}_seed{42,43,44}/` | ✅ **완료** — §3-2·3-3·`RESULTS_2ND.md`에 기록됨 |
| 4단계 | 전문가 톤 진단 생성 — Solar Pro3(교사)가 640건에 코멘트 생성 → 믿:음 LoRA(학생)로 증류 | 증류 학습 산출물 | ❌ **미구현** — teacher/distillation 관련 파일 검색 결과 0건 |

**즉 계획한 4단계 중 3단계(태깅 확장)만 끝났고, 1·2·4단계(서비스 채점 엔진 이식·또래 비교·
진단 코멘트 생성)는 계획 문서로만 존재한다.** §3-4·3-6에서 다룬 "전문가 채점 규칙"·
"하이브리드 등급 모델"은 `20_AIHub_data` 안에서 검증까지 끝난 **연구 결과**이고, 이를
실제 화면에 붙이는 이식 작업(1·2단계) 자체가 착수되지 않았다.

## 6. 한계 (의도적으로 남긴 것)

- **Validation 라벨 미확보** — held-out 62건은 여전히 Training 640건 내부 분할이다. AI Hub
  로그인이 있는 사람이 `VL_1.언어적_*.zip`을 받아야 해소된다.
- **n=640, 시드 분산 실재** — 모든 수치는 3시드 평균±sd로 읽어야 하며 단일 시드 수치는
  신뢰하지 않는다.
- **원천 오디오 파손** — 음성 질(voc_quality) 항목은 학습·서비스 양쪽에서 제외했다.
- **비언어적(제스처) 데이터 미사용** — 서비스 범위(카메라 미사용) 밖.
- **오라클(사람 주석 카운트) 상한은 서비스에서 재현 불가** — 서비스는 우리 태거가 직접 센
  카운트를 쓰므로 실제 성능은 §3-6 수치보다 낮을 수 있다. 이 실측은 아직 안 됐다.
