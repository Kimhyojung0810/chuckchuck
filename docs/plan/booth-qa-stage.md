넷 다 공개 방문자에게는 잠긴다(`app.js BETA_ROUTES`). 부스 노트북은 `/auth` 에서 팀 코드로 개발자 모드를 한 번 켠다.
주소창 경로 → 해시 리다이렉트는 `demo/bridge.py hash_route` 라서 **8799(systemd) 는 재시작해야 `/booth/qa` 가 먹는다**
(`#/booth/qa` 는 바로 된다).

## 2. 흐름 (화면 다섯 장, body 위 `#bqStage` 층)

시작(고정) → 발표 고르기 → 훑어보기 + 질문 준비 → Q&A 무대(`#/qa`) → 마무리 → 40초 뒤 자동으로 시작

- **시작** — 한 문장 소개 · 「체험 시작하기」 · 심사위원단 병아리 넷 · 「예시 질문」 말풍선. 카메라 앞에 사람이 서면 병아리가 인사한다.
- **발표 고르기** — `BOOTH_DECKS`(js/booth_qa.js)에 적힌 덱 중 **지난 파싱본이 있는 것만**. 표지는 실제 미리보기 PDF 1쪽.
- **훑어보기 + 준비** — 슬라이드가 3.6초마다 넘어가고, 오른쪽에 실제 진행 단계(자료 → 개념 → 연결 → 질문 3개). 실측 46~61초(첫 체험), 같은 덱 두 번째부터 약 11초(브리지가 개념·그래프를 재사용).
- **Q&A 무대** — 지금 답할 질문(되묻기 포함)을 큰 카드로, 판정·힌트는 아래 대화 칸, 오른쪽엔 질문이 가리키는 슬라이드와 내 모습.
- **마무리** — 질문 3개의 결과 칩 · 「질문을 받는 동안 얼굴이 정면으로 잡힌 시간」 · 처음으로. **코칭 기록(qa-history)에 남기지 않는다** — 다음 방문객이 본다.

로직은 새로 만들지 않았다. 덱 되살리기·선분석·질문 생성은 `#/test/qa`(startTestDeck 자료만 경로)와 같은 함수,
질문·판정은 `qa_live.js` 그대로다(`renderQaLive`·`qaLiveEnd` 에 분기 한 줄씩). 트랙은 `"5"`(질문 3개, 함정 1개).

## 3. 카메라 판단 (OpenCV.js) — `js/booth_cv.js` · `js/booth_cv_worker.js`

| 기능 | OpenCV | 어디에 |
|---|---|---|
| 사람이 다가옴 | Haar 정면 얼굴(`CascadeClassifier`) + 프레임 차(`absdiff`→`threshold`→`countNonZero`) | 시작 화면 인사 |
| 구도 안내 | 얼굴 상자 위치·크기 | 무대 내 모습 창 「화면 가운데로 조금 와 주세요」 등 |
| 얼굴 테두리 | 얼굴 상자 | 무대 내 모습 창 |
| 정면으로 잡힌 시간 | Haar 정면 분류기가 얼굴을 찾은 프레임 비율 | 무대(실시간) · 마무리 카드 |

- **워커에서 돈다.** OpenCV.js(10MB)를 메인 스레드에서 올리면 헤드리스 크롬이 2분 넘게 멈췄다. 워커에서는 0.7~1.2초.
- **이 빌드의 Module 은 thenable** 이라 Promise 로 resolve 하면 끝없이 돈다 — 준비 신호만 기다린다(`cvReady`).
- 프레임은 320px 로 줄여 워커로 보내고 결과만 받는다. **서버로 보내지 않는다** (시작 화면 아래 문구).
- 못 받으면 카메라 판단 없이 그대로 돈다. 부스 인터넷이 느리면 `js/vendor/opencv.js`·`js/vendor/haarcascade_frontalface_default.xml`
  에 사본을 두면 먼저 쓴다(git 에는 안 올린다).
- 워커 `?v=` 는 `booth_cv.js` 안에서 손으로 올린다 — `scripts/chk bump` 는 index.html 만 본다.

## 4. 부스 전날 준비

1. 부스 노트북에서 `/auth` → 팀 코드.
2. 부스용 덱을 `/test/qa` 에서 한 번씩 열어 **파싱본을 만든다** (`/booth/qa` 는 파싱본이 있는 덱만 보여 준다. 보관 기간 `DEMO_CACHE_TTL_HOURS` 기본 24시간 — 날마다 아침에 한 번).
3. 각 덱을 `/booth/qa` 로 한 번 끝까지 돌려 두면, 그날 두 번째 체험부터 준비가 약 11초다.
4. 카메라 권한을 한 번 허용해 둔다(시작 화면에서 묻는다).

## 7. 화상 통화판 — `/booth/call` (2026-10-01)

> 사용자 요청(10/1): "부스를 위해서 만드는 전용 QA 페이지 … 왼쪽 하단에는 삐약이가 나와서 QA 를 진행하고(교수님이건, 어떤 역할이던
> 위임을 받게 됨) 나는 정면에 그대로 나와서 그 질문에 대한 답을 이어서 … 내 대화와 삐약이 대화가 애플 liquid glass 처럼 은은하게 오버레이."

같은 부스 흐름(시작 → 발표 고르기 → 훑어보기 → 질문 3개 → 마무리 → 40초 뒤 처음)에서 두 곳만 다르다.

| 어디 | `/booth/qa` | `/booth/call` |
|---|---|---|
| 발표 고르기 | 덱만 고른다 | 덱 위에 **삐약이에게 맡길 역할** 4개(교수님 · 심사위원 · 회사 상사 · 일반 청중, 기본 교수님) |
| 질문 화면 | 큰 질문 카드 + 대화 칸 + 오른쪽 자료·내 모습 | **내 얼굴(웹캠)이 화면 전체**. 왼쪽 아래 역할 이름표를 단 삐약이, 그 위로 질문·내 답·판정이 리퀴드 글라스 말풍선으로 쌓인다. 오른쪽 위 질문이 가리키는 장, 아래 띠 답 칸 |

- **질문·판정 로직은 그대로다.** 역할은 `qa.aud`(말풍선 이름표)로만 쓰이고 질문·판정 요청에 실리지 않는다 —
  역할에 따라 질문 내용이 바뀌지 않는다. 그래서 고르는 칸도 「누가 묻는 자리인지」만 적는다.
  역할별로 다른 질문이 필요하면 QA 로직 일이다([qa-persona-questions.plan.md](qa-persona-questions.plan.md)).
- 파일: `js/booth_call.js`(질문 화면 한 장) · `css/booth_call.css`(글라스) · `js/booth_qa.js`(무대 종류 `bq.variant`, 역할 고르기).
  탭이 무대 종류를 기억한다(sessionStorage `cheokcheok:booth-qa` = `1` 무대 · `call` 화상판) — `#/qa` 새로고침해도 같은 배치.
- 배치 규칙: 얼굴 가운데(가로 38~62% · 세로 18~62%)에 글라스를 두지 않는다(9/22 회의안 1-2). 지금 답할 질문만 또렷하고 크게,
  지난 질문까지의 말은 옅게(.58) 물러난다. 대화는 늘 맨 아래(삐약이 바로 위)에 붙는다. 삐약이가 새 말을 하면 2.6초 말하는 모습.
- 글라스: `backdrop-filter: blur(22px) saturate(1.8)` + 비스듬한 빛 + 위쪽 하이라이트. 흐림을 못 하는 브라우저 ·
  「투명도 줄이기」 사용자는 같은 자리에 진한 면.
- 카메라 판단(구도 안내 · 정면 비율)은 `/booth/qa` 와 같다. 얼굴 테두리는 화상판에서 그리지 않는다(얼굴 위에 선을 긋지 않게).

검증: `labs/booth_qa/run.py --route call --role 회사 상사` — 배치 검사에 `center_cover`(얼굴 가운데를 덮는 요소)가 있다.
