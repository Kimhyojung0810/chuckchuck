## 0. 한 문장

**캡처 한 장 = 슬라이드 한 장.** 화면 캡처를 Upstage Document Parse 에 이미지로 넣으면 1페이지 SlideDoc 이 되고,
여러 장은 `merge_slidedocs` 로 한 자료가 되어 F-06 → F-07 → F-08 → F-09 가 **그대로** 돈다. 새 vision 모델은 없다.

## 1. 왜 별도 페이지인가

- 앱의 `#/qa` 는 `pipelineQaReady()` 가 graph·alignment·flow 셋을 요구한다. 발화 없는 체험은 alignment·flow 가 없다.
- 헌장 §0 "Festa 전 프론트 새 화면 금지" 는 `app.js` 가 깨질 위험 때문이다. `booth.html` + `js/booth.js` + `css/booth.css` 는
  `app.js`·`index.html` 을 한 줄도 건드리지 않고, API 클라이언트(`chuckchuck_bridge.js`)만 import 해서 요청 본문 계약을 앱과 같게 맞춘다.
- 별도 저장소·상위 폴더는 **아니다.** 브리지·contracts·`.env`·세션 보관소를 그대로 써야 하므로 저장소 안에 둔다.

## 6. 카메라로 찍기 · 말해서 답하기 · 읽어 주기 (2026-09-18)

**왜** — 9/16 판은 「화면 공유 또는 스크린샷 → 타이핑 답」이었다. 부스 방문객은 자료를 폰에 들고 오고,
서서 타이핑하지 않는다. 참여 문턱을 카메라(찍는다)와 마이크(말한다)로 낮춘다. 소리는 기본 무음(UI_REDESIGN §14).

| 무엇 | 어디 | 어떻게 |
|---|---|---|
| 카메라로 찍기 | `booth.js openCamera/grabFrame` | `getUserMedia({facingMode:'environment'})` 미리보기 → 「찍기」로 한 장씩. 카메라가 둘 이상이면 「카메라 바꾸기」(폰 앞/뒤 · 노트북 + USB 문서 카메라). 사진은 JPEG 0.9, 화면 캡처는 PNG |
| 미리보기 못 여는 곳 | `captureRoutes` (booth_logic) | http 로 들어온 폰·권한 거부 → `<input capture="environment">` 로 기기 카메라 앱. 버튼 이름이 「사진 찍어 올리기」로 바뀐다 |
| 폰 사진 정리 | `normalizeImage` | `createImageBitmap(imageOrientation:'from-image')` 로 EXIF 회전을 풀고 긴 변 1600 JPEG 로. 12MP 사진이 100~200KB 가 된다 |
| 말해서 답하기 | `toggleMic/startDictation/startRecording` | 앱과 같은 길: 크롬은 실시간 받아쓰기(Web Speech), 죽으면 녹음 + 서버 STT(`/api/v1/transcribe`). **채워만 주고 보내지 않는다** — 확인 뒤 「답하기」 |
| 읽어 주기 | `speak/setSound` | `speechSynthesis` ko-KR. 기본 꺼짐, 「소리 켜기」로 켜면 질문·힌트·판정을 **화면에 있는 말 그대로** 읽는다(`speakableJudgement`). 마이크를 켜면 읽기를 멈춘다(코치 목소리를 받아쓰지 않게) |
| 손가락 기기 | `booth.css @media (pointer: coarse)` | 버튼 48px, 마이크 버튼 한 줄 전체. 폰에서는 입력창 자동 포커스를 안 한다(키보드가 마이크를 가린다) |
| 어느 버튼이 주인공인가 | `captureRoutes.primary` | 폰은 카메라, 부스 노트북은 화면 공유(자료가 열린 창을 고르는 게 제일 빠르다) |

순수 판단은 `js/booth_logic.js` 로 빼서 `node tests/js/booth.smoke.mjs`(18 케이스, 마지막은 자기검사)가 잡는다.
`scripts/chk gate` 가 `tests/js/*.smoke.mjs` 를 전부 돌리고, `?v=` 검사가 `booth.html` 과 `js/booth.js` 의 import 까지 본다.

### 6-0. 통화 모드 (2026-09-18 저녁) — "화상통화를 한다는 느낌이어야 해"

질문 단계를 카드가 아니라 **통화 화면**으로 바꿨다. 카메라는 자료를 읽는 창이 아니라 **내가 상대를 마주 보는 창**이다.

| 층 | 무엇 | 어디 |
|---|---|---|
| 바탕 | 내 모습 (앞카메라/웹캠, 거울처럼 뒤집음). 못 열면 "목소리로 통화해요" | `openSelfView` · `.call-self` |
| 상대 타일 | 객석 병아리 한 마리(`Chatter.chickSvg('solar')`). 기분은 `data-mood` 로 chatter.css 가 그린다 — 묻는 중 curious, 잘 답하면 happy, 어긋나면 grumpy. 듣는 중엔 타일 테두리가 브랜드색 | `mountPartner/setPhase` · `partnerMood` |
| 말풍선 | 상대(왼쪽): 질문·힌트·판정(pill+반응+요약)·빠진 것·되묻기/정답 요지. 나(오른쪽): 보낸 답. 위로 갈수록 흐려지고 8개만 남는다 | `bubble` · `judgementBubbles` |
| 자막 | 내 말이 실시간으로 채워지는 입력창. **눌러서 고칠 수 있다** | `.call-caption #qa-answer` |
| 자동 대화 | 기본 켬. 질문(읽어 주기 켜면 읽기가 끝난 뒤) → 듣기 → 2.5초 침묵 → **3초 카운트다운** → 보내기. 자막을 누르면 멈춘다. 되물으면 다시 듣는다. 녹음+STT 폴백에서는 침묵 판정이 없어 「녹음 멈추고 받아쓰기」를 눌러야 한다 | `markSpeech/watchQuiet/startCountdown` · `speechSettled/countdownText` |
| 조작 | 말해서 답하기 · 답하기 · 힌트 · 모르겠어요 · (판정 뒤) 다시 답하기 · 다음 질문/통화 마치기. 위 도구줄: 자동 대화 · 소리 · 카메라 · 작은 창 · 통화 마치기 | `.call-controls` · `.booth-qa-tools` |

**재질은 글라스다** (사용자: "애플의 glass"). 오버레이 전부가 `.glass` 한 규칙을 나눠 쓴다 — 블러 18px + 채도 1.7, 얇은 반사 테두리,
위쪽 하이라이트, 캡슐 버튼, 누르면 밝아짐. 블러를 못 하는 브라우저와 「투명도 줄이기」 설정에선 불투명에 가깝게 떨어진다.
MVP_SPEC §3 의 glassmorphism 금지는 **앱 화면**(#/, #/qa …) 규율이고, 통화 화면은 객석·극장 계열이라 그 밖이다 — 사용자 결정.
말풍선은 왼쪽 60%(폰 70%) 안에만 서서 얼굴 가운데를 비운다. 아래 묶음(자막+조작줄)은 흐름 배치라 조작줄이 몇 줄이 돼도 자막을 덮지 않는다.

**실제로 봤다.** 이 서버에 브라우저가 없어 헤드리스 크롬 + 가짜 카메라 실험실을 만들었다 — [`labs/qa_call/`](../../labs/qa_call/README.md).
담기→분석→질문→답→판정→힌트→포기→마침 7단계가 실 API(8801)로 데스크톱·폰 둘 다 콘솔 오류 0으로 돌았고, 사진이 `labs/qa_call/out/` 에 남는다.
못 보는 건 실제 마이크·실시간 받아쓰기·TTS (헤드리스에 음성이 없다) — 이건 부스 리허설(§6-2)에서만.

"채워만 주고 보내지 않는다" 규율은 **카운트다운으로 바꿨다** — 자동으로 보내되 몰래 보내지 않고, 고칠 틈이 눈에 보인다.
자동 대화를 끄면 옛 규율 그대로다(멈추고 확인하고 답하기). 소리는 여전히 기본 무음이라, 켜지 않으면 상대는 말풍선으로만 말한다.

## 7. 발표 모드 · 페이스타임 배치 (2026-09-23)

**왜** — 9/18 판 통화 화면은 **질문부터** 시작했다. 부스 방문객은 자료를 찍고 나면 바로 질문을 받는다.
사용자 요청(9/23): "발표를 하는 와중에도 삐약이가 시무룩해하면서 너무 말이 빨라요·느려요·똑같은 말을 많이 해요·
'어' '음' 을 많이 써요·산만하게 움직여요 … 비슷한 상황 전부", 그리고 "페이스타임처럼 발표 중엔 자료가 크고
내 얼굴이 작게, 질문할 때는 반대로". 그래서 통화가 **발표 모드로 먼저 열리고**, 「질문 받기」를 눌러야 Q&A 로 간다.

### 7-1. 무엇을 만들었나

| 무엇 | 어디 | 어떻게 |
|---|---|---|
| 페이스타임 배치 | `booth.css .call[data-main]` · `setMain/swapMain` | 무대 둘(자료 `#call-slides` · 내 모습 `#call-self`) 중 `data-main` 쪽이 프레임을 채우고 나머지가 오른쪽 아래 작은 창. **작은 창을 누르면 자리가 바뀐다**(메인을 누르면 아무 일도 안 한다). 발표=자료 메인, Q&A=내 모습 메인 |
| 작은 창이 조작줄을 안 덮게 | `ResizeObserver` → `--dock-h` | 아래 묶음 높이를 잴 때마다 CSS 변수로 넘긴다. 조작줄이 폰에서 두 줄이 돼도 작은 창이 그 위에 선다 |
| 자료 넘기기 | `renderSlide/stepSlide` | 담은 장면이 슬라이드다. 「이전/다음 장면」·키보드 ←→·말로 「다음 장면」. Q&A 로 가면 질문의 `slide_nos[0]` 장면이 작은 창에 뜬다 |
| 발표 피드백 | `deliveryObserve`(booth_logic) ← `startPresentDictation`·`startSensors` | 받아쓰기 글자 수 + 웹캠 프레임 차 + 마이크 RMS 를 0.25초마다 계기에 넣고, 지적이 나오면 말풍선 한 줄 + 삐약이의 무안한 얼굴(땀방울·홍조·시선 내림, 4.5초). **LLM 도 서버도 안 쓴다** |
| 말풍선 기록 | `bubble()` | 더 이상 치우지 않는다(9/23). 양쪽 가장 새 풍선에만 꼬리(`is-latest`)가 붙어 지금 말하는 쪽을 가리키고, 위로 스크롤하면 이전 질문·답이 그대로 있다. 판정은 여전히 **한 풍선**(`judgementBubble`) |
| 읽어 주지 않는다 | `showTell` | 지적은 TTS 로 읽지 않는다 — 마이크가 켜져 있어서 코치 목소리를 그대로 받아쓴다 |
| 마친 화면 | `deliverySummary` → `#qa-delivery` | 「발표 중 알려 준 것 · 빠름 2 · 간투어 1」. 지적이 없었으면 줄 자체가 없다 |

### 7-2. 지적 7종 + 칭찬 — 문턱과 출처

문턱은 전부 `js/booth_logic.js` 의 `DELIVERY` 한 곳에 있다. 쿨다운 12초(지적 사이) · 같은 종류 45초 · 칭찬 60초.

| 지적 | 조건 | 어디서 온 값인가 |
|---|---|---|
| 빠름 `fast` | 15초 창에서 402자/분 초과 (창 안 25자·6초 이상 말해야 잰다) | `CPM_REC.max 350 × 1.15` — **app.js 의 `cpmJudge` 와 같은 배수**. 앱 리포트와 부스가 다른 말을 하면 안 된다 |
| 느림 `slow` | 같은 창에서 255자/분 미만 | `CPM_REC.min 300 × 0.85` (같은 출처) |
| 간투어 `filler` | 최근 30초에 간투어 3개 이상 | 낱말 목록은 `f18_habits.FILLERS` 의 거울 — 서버가 세는 것과 같은 낱말만 센다 |
| 반복 `repeat` | 최근 30초에 같은 낱말 4번, 또는 접두 더듬기 2번("지도 지도력은") | f18 의 `REP` 규칙과 같다 |
| 멈춤 `pause` | 말한 적이 있고 글자가 5초 동안 안 늚 | `f18_habits.PAUSE_SEC` 와 같은 5초 |
| 움직임 `fidget` | 최근 5초 프레임 차 평균 > 12 (32×18 회색, 표본 8개 이상) | **실측이 아니다** — 리허설 보정값. 정지 화면 잡음 2~4, 몸 흔들림 8~15 를 가정했다 |
| 작은 목소리 `quiet` | 최근 6초 RMS 평균 < 0.015 이고 그동안 글자가 10자 이상 늘었다 | **실측이 아니다** — 보통 말소리 0.05~0.2 가정. 부스 마이크·홀 소음에서 다시 잡아야 한다 |
| 안정 `steady` | 권장 속도로 60초 이어 말했고 그 창에 60자 이상 | 칭찬은 60초에 한 번. 마친 화면 요약에는 안 센다 |

웹캠 프레임은 32×18 회색으로 줄여 **평균 절대차만** 본다. 얼굴을 알아보지 않고, 아무것도 서버로 보내지 않는다.

**계기와 기준 맞추기 (운영자용).** 움직임·음량의 절대값은 웹캠·마이크·조명마다 다르다. 그래서 부스에서 눈으로 보고 맞춘다.

1. 부스 크롬에서 `booth.html?meter=1` 로 연다 (또는 발표 모드 도구줄의 「계기 보기」).
2. 왼쪽 위 계기에 `움직임 3.2 / 기준 12 · 음량 0.041 / 기준 0.015 · 빠르기 312자/분 · 간투어 1` 처럼 **지금 값 / 지금 기준**이 뜬다. 못 잰 것은 `—` 다.
3. 발표할 사람이 **가만히·조용히** 앉은 채 「기준 맞추기 (5초 가만히)」를 누른다 → 5초 동안 모은 바닥값으로
   `fidgetMotion = max(8, 바닥×3)` · `quietLevel = max(0.006, 바닥×4)` (`calibrateDelivery`) 를 잡아 `localStorage['cheokcheok:booth-delivery']` 에 저장한다. 되돌리려면 「기본값으로」.
4. 그 다음 7종을 **일부러 하나씩** 내 본다 — 빨리 말하기 · 느리게 · 「어 음」 · 같은 말 4번 · 5초 침묵 · 몸 흔들기 · 작게 말하기.
   뜨는 것과 안 뜨는 것을 적어 두고, 안 뜨면 3번을 다시 하거나 `DELIVERY` 를 고친다.

계기는 방문객 화면이 아니다 — 기본 숨김이고, Q&A 로 넘어가면 자동으로 닫힌다.

**이 서버에서 확인한 것** (`labs/qa_call/run.py present`, 헤드리스 크롬 + 가짜 카메라 + `window.boothLab.feed`):
발표 모드로 열림 · 간투어 지적 말풍선 + 땀방울(`data-tell="awkward"`) · 움직임 지적 · 작은 창 눌러 자리 바꾸기 ·
발표 시계 · 계기 숫자 · 판정은 한 풍선이고 앞 질문·답이 남아 있음 · 콘솔 오류 0 (데스크톱 1280×860 · 폰 390×844).

**이 서버에서 확인할 수 없는 것** (리허설 몫 — §6-2 에 이어서):
- **실제 마이크와 Web Speech 지연** — 헤드리스는 구글 음성 서버에 못 붙는다. 실시간 지적이 *체감상* 늦지 않은지는 사람이 말해 봐야 안다.
- **움직임·음량 문턱** — 위 7-2 의 두 값은 가정이다. 기준 맞추기로 보정한다.
- 부스 홀 소음에서 남의 말소리가 받아쓰기에 섞이는지 (섞이면 지향성 마이크·헤드셋).

### 7-3. 더 넓힐 수 있는 것 (후보)

지금은 **브라우저 안에서 공짜로 잴 수 있는 것**만 한다. 아래는 다음에 붙일 수 있는 것과 그 대가다.

| 후보 | 어떻게 | 되나 |
|---|---|---|
| 시선·딴 데 보기 | `FaceDetector` 는 크롬에서도 플래그·불안정. 제대로 하려면 MediaPipe Face Mesh(WASM 3MB+) | **무겁다.** 부스 노트북 한 대에 발표+분석이 같이 도는데 프레임마다 랜드마크를 돌리면 통화가 끊긴다. 결선 데모용으로만 |
| 화면 밖으로 나감 · 구도 | 얼굴 bbox 하나면 된다 (`FaceDetector` 또는 가벼운 blazeface) | 시선보다 싸다. "얼굴이 화면 아래로 잘렸어요" 한 줄이면 값을 한다 |
| 단조로운 톤 | 자기상관 피치 추정 → 30초 창의 피치 분산 | `AnalyserNode` 로 이미 소리를 받고 있어 추가 비용이 적다. 다만 잡음에서 피치가 튄다 — 리허설 보정 필수 |
| 음량 기복 | 지금 재는 RMS 의 분산 | 거의 공짜. 「작은 목소리」 옆에 바로 붙일 수 있다 |
| 장면당 시간 vs F-17 권장 속도 | 이제 **장면 전환 시각**이 있다(`stepSlide`) — 장면별 체류를 잰다 | 됨. F-17 권장 pace 를 부스 화면이 처음 쓰는 자리가 된다 |
| 말과 장면이 어긋남 (실시간) | F-11 정합 호출(1.5초)을 장면 전환마다 | 서버 왕복이 붙는다. "지금 말이 이 장면과 다른 것 같아요" 는 세 마디 중 하나만 맞아도 신뢰를 잃는다 — 정확도부터 재야 한다 |
| 대본 읽는 말투 | 끊김 없이 일정한 속도 + 간투어 0 + 문장 길이 균일 | 지금 재는 값만으로 규칙을 세울 수 있다. 단 "잘하는 사람"을 지적하게 될 위험이 크다 |
| 끝맺는 말 잡기 | 「이상입니다」「감사합니다」 정규식 → 「질문 받기」 권유 | 쉽다. `PRESENT_COMMANDS` 옆에 한 줄 |
| 질문 타이밍 예측 | [qa-cam-overlay.plan.md](qa-cam-overlay.plan.md) 의 디렉터 | 그 문서의 설계를 그대로 쓸 수 있다. 부스에서는 사람이 「질문 받기」를 누르는 게 더 정직하다 |
| Zoom 으로 송출 | OBS 가상 카메라 ([qa-cam-overlay.plan.md](qa-cam-overlay.plan.md) §5) | 통화 화면이 이미 한 프레임이라 창만 잡으면 된다. 장비(OBS) 몫 |
| 지적을 F-19 리포트로 | `deliverySummary` 의 counts 를 리포트 습관 절에 얹기 | 값을 보내는 길만 열면 된다. 다만 **부스 측정은 F-18 서버 측정과 다른 잣대다** — 같은 표에 섞으면 숫자가 거짓말이 된다. 따로 적어야 한다 |
