# 화상 캠 위에 삐약이 질문 실시간 오버레이 (2026-09-22 설계안)

> 사용자 요청(9/22): "QA 를 할 때 카메라 기반 화상 캠에서 **실시간으로 삐약이가 하는 질문**을 **화상 공간에 overlay**"
> 상태: **설계만.** 코드는 손대지 않았다. 부스 통화 모드([booth-screen-qa §6-0](booth-screen-qa.plan.md)) 위에 얹는다.
> 모델 라우팅(`/ecc:model-route`): 설계·아키텍처 = **opus** (확신 높음) · 구현 = **sonnet** · CSS/스모크 = **haiku**. 근거는 §9.

## 0. 한 문장

**질문은 미리 만들고, "언제 묻느냐"만 실시간으로 정한다.** 삐약이는 발표자의 말을 듣다가 개념이 끝나는 순간 손을 들고,
질문은 웹캠 프레임 **안에** 자막처럼 얹힌다. 그 프레임은 그대로 Zoom·Meet 같은 화상 공간에 가상 카메라로 내보낼 수 있다.

## 2. 요청을 두 층으로 읽는다

"화상 공간에 overlay" 는 두 뜻이 있고 둘 다 필요하다. 층을 나누면 A 만으로도 부스 데모가 되고, B 는 A 의 출력을 그대로 쓴다.

| 층 | 뜻 | 사용자 | 결과물 |
|---|---|---|---|
| **A. 프레임 안 오버레이** | 우리 페이지의 웹캠 화면 **프레임 자체에** 질문·삐약이·자막을 합성 | 부스 방문객 · 혼자 연습하는 발표자 | `<canvas>` 한 장 = 합성된 영상 |
| **B. 화상 공간 송출** | A 의 합성 영상을 Zoom·Meet·Discord 에 **내 카메라로** 내보내기 | 실제 온라인 발표 리허설 · 심사 데모 | 가상 카메라 |

지금 통화 모드는 A 의 "DOM 오버레이" 판이다. A 를 **canvas 합성**으로 바꾸는 것이 이번 일의 핵심이고, 그래야 B 가 공짜로 따라온다.

## 3. 아키텍처 — 층 4개

```
[웹캠 MediaStream] ─┐
                    ├─ compositor (rAF 30fps) ─► <canvas id="stage"> ─► 화면(A) ─► captureStream() ─► OBS/가상카메라(B)
[오버레이 상태]  ───┘         ▲
   · 지금 질문 · 삐약이 화자·기분 · 발표자 자막 · 판정 pill · "손 들기" 예고
                              │
[디렉터] ◄── 받아쓰기(interim/final) ◄── Web Speech / 서버 STT
   · 개념 매칭(로컬) · 침묵 감지(있음) · 질문 큐 · 언제 묻나
                              │
[브리지 API] F-08 사전 생성 · F-09 판정만 실시간 · (선택) F-12 한 줄 반응
```

| 층 | 새 파일 | 하는 일 | 안 하는 일 |
|---|---|---|---|
| **compositor** | `js/booth_stage.js` | 웹캠 프레임을 canvas 에 그리고(거울 반전 유지) 위에 오버레이를 **그린다**. 텍스트는 `OffscreenCanvas` 에 한 번 렌더해 캐시, 프레임마다 다시 조판하지 않는다 | LLM 호출 · 상태 판단 |
| **overlay state** | `js/booth_overlay_state.js` (순수 함수) | `{question, speaker, mood, caption, verdict, handRaised, layout}` 하나. DOM 도 canvas 도 이 상태만 읽는다 | 부수효과 |
| **director** | `js/booth_director.js` (순수 판단 + 얇은 타이머) | 받아쓰기 텍스트 → 개념 노드 매칭 → "손 들기" → 침묵 → 질문 꺼내기 (§4) | 네트워크 |
| **transport (B)** | 없음 (OBS) 또는 `js/booth_cast.js` | `stage.captureStream(30)` 를 OBS 브라우저 소스로 넘기거나, 같은 탭 안 `<video>` 로 보여 주기 (§5) | WebRTC 방 만들기 |

**왜 DOM 오버레이를 버리고 canvas 로 가나.** 화상 공간(B)은 DOM 을 못 받는다. 카메라로 들어가는 건 픽셀뿐이다.
A 와 B 가 같은 픽셀을 보게 하려면 합성 지점이 하나여야 하고, 그게 canvas 다. DOM 은 **조작줄(버튼·입력창)** 로만 남긴다 — 조작줄은 송출하지 않는다.

**접근성 규율.** canvas 안 글은 스크린리더가 못 읽는다. 오버레이 상태가 바뀔 때마다 숨긴 `aria-live` 영역(`#stage-a11y`)에 같은 문장을 쓴다. 지금 `call-log` 의 `aria-live="polite"` 역할을 이것이 이어받는다.

## 4. "실시간" 의 정의 — 질문은 미리, 타이밍은 지금

F-08 은 6.4초라 대화 안에서 부를 수 없다. 대신 **질문 풀은 사전 생성**(지금과 같음)하고, 디렉터가 발표자의 말을 들으며 **어느 질문을 언제 꺼낼지**만 정한다.

| 단계 | 신호 | 판단 | 오버레이 |
|---|---|---|---|
| 듣기 | Web Speech `interim` | 없음 | 발표자 자막(아래 띠, 최근 2줄) |
| 개념 감지 | `final` 문장 누적 | 문장 안 낱말 ↔ `ConceptGraph.nodes[].label/aliases` 매칭(로컬, <50ms). 노드마다 `node_id` 로 걸린 질문이 풀에 있으면 후보 | 삐약이 타일이 **살짝 손을 든다** (`handRaised`, 기분 curious) — 발표자가 "질문이 오겠구나" 를 미리 안다 |
| 물을 타이밍 | 침묵 2.5초 (기존 `watchQuiet`) **또는** 발표자가 「질문 받을게요」 류 트리거 문장 | 후보 중 `severity` 높은 것 하나. 후보 없으면 풀에서 순서대로 | 질문 말풍선이 프레임 안에 뜬다. 소리 켜면 읽는다(기존 `speak`) |
| 답 | 받아쓰기 → 침묵 → 카운트다운 (기존) | F-09 판정 1.6초 | 판정 pill + 한 줄 요약 + 삐약이 기분(happy/grumpy) |
| 되묻기 | F-09 `followup` 있으면 | 같은 질문 라운드 2 | 말풍선 갈아끼움 |

**왜 임베딩·LLM 매칭이 아니라 낱말 매칭인가.** 개념 라벨은 F-06 이 이미 뽑아 둔 명사구다. 부스 발표 3~5분에 노드 10~20개면 낱말 포함 검사로 충분하고,
틀려도 "순서대로" 폴백이 있어 대화가 멈추지 않는다. 정확도가 부족하면 그때 브리지에 `/api/v1/alignment` 경량 호출(F-11 실측 1.47초)을 붙인다 — 첫 판에는 넣지 않는다.

**삐약이 화자 배정.** 질문마다 `speaker` 를 정한다. `contracts.py` 의 F-12 배역(ax=발표를 들음, midm=믿음/검증, exaone=전문가 칭찬, solar=…)을 그대로 쓴다:
검증형(`trap`·근거 요구) 질문 → midm, 청중 관점 질문 → ax, 나머지 → solar. 판정 뒤 한 줄 반응이 필요하면 F-12 `MockLLM` 수다 스크립트 형식을 재사용(추가 LLM 호출 없음).

## 5. 화상 공간으로 내보내기 (B) — 코드 최소 순서

| 안 | 방법 | 코드 | 장점 | 한계 |
|---|---|---|---|---|
| **B-1 (권장, 첫 판)** | OBS 브라우저 소스로 `booth.html?cast=1` 을 열고 **OBS Virtual Camera** 를 Zoom/Meet 카메라로 선택 | `?cast=1` 이면 조작줄 숨기고 stage 만 꽉 채움. 그게 전부 | 어떤 화상 앱이든 됨. 심사 데모에서 제일 안전 | OBS 설치 필요. 마이크는 그대로 실제 마이크 |
| B-2 | `stage.captureStream()` → 같은 페이지 미리보기 `<video>` | 10줄 | OBS 없이 "송출 화면" 확인 | 화상 앱으로는 못 나감 |
| B-3 | 가상 카메라 드라이버 (v4l2loopback + ffmpeg / macOS 는 OBS 가 유일 실용) | 셸 스크립트 | 브라우저 없이 | OS 마다 다름. 부스에서 안 함 |
| B-4 | 자체 WebRTC 방 | 서버·시그널링 | — | **하지 않는다.** 화상 공간을 우리가 만들 이유가 없다 |

주의 두 가지. (1) OBS 브라우저 소스 안에서는 **웹캠 권한 팝업이 안 뜬다** — OBS 는 페이지에 카메라 권한을 자동 허용하지만 마이크 받아쓰기(Web Speech)는 OBS CEF 에서 불안정하다.
→ `?cast=1` 모드는 **보기 전용**, 디렉터(듣기·판정)는 일반 크롬 탭에서 돌리고 상태를 `BroadcastChannel('booth-stage')` 로 OBS 쪽 탭에 보낸다. 두 탭이 같은 상태를 그린다 (§3 의 "상태 하나" 가 여기서 값을 한다).
(2) 발표자 얼굴이 카메라로 나가므로 **동의 문구**가 한 번 더 필요하다 (booth-operations 의 세션 동의와 별개: "이 화면이 화상 통화에 카메라로 나갑니다").

## 8. 팀 결정이 필요한 것

1. **B 를 Festa 범위에 넣나.** A(프레임 안 오버레이)만으로 부스 데모는 된다. B 는 OBS 설치와 리허설 시간이 든다. 결선(11월) 시그니처로 미루는 안이 있다.
2. **손 들기 예고를 보여 줄 것인가.** 발표자에게 "곧 질문 온다" 를 미리 알리면 부담이 줄지만, 실제 청중은 예고하지 않는다. 기본 켬 + 끄기 버튼 제안.
3. **얼굴 가리지 않기.** 지금은 말풍선을 왼쪽 60% 로 제한한다. 브라우저 `FaceDetector`(크롬 실험 플래그)는 부스 컴퓨터에서 못 믿는다 → 첫 판은 고정 배치 유지, 사용자가 말풍선을 드래그로 옮길 수 있게만.
4. **삐약이 이름.** UI_REDESIGN §열린 질문의 "무대감독 병아리 이름" 과 같은 결정. 오버레이에 이름표가 찍히므로 이번에 정해야 한다.
