# 자료를 올리면 맞춤으로 — 상황 추정 + 청중이 기대하는 내용 제안

> 사용자 제안 2026-09-12: "PPT 가 업로드됐을 때 맞춤으로 제안해 주면 좋겠다. 내용도 우리가 제안해 주는 기능."
> 상태: 설계. Festa(10/6) 전에는 **서버 쪽만** 만들고 화면은 기존 입력 폼을 미리 채우는 정도로 제한한다 (헌장 §0).

## 지금 화면이 하는 것

`#/new` 폼에서 사용자가 상황(`nf.occ` → `situation`)·청중(`nf.ctx` → `audience`)·시간을 **직접** 고른다.
이 값은 F-06·07·11 프롬프트 한 줄, 채점표 가중치(`rubric_v3.resolve_situation`), 리포트 「‘…’에 맞춰 봤어요」 문구에 쓰인다.
F-20(`/api/v1/strategy`)은 발표가 끝난 뒤 **구성 재배치**(결론 위치 early/late/throughline)를 제안한다 — 내용 보완은 안 한다.

## 1. 상황 추정 — "이 자료는 업무 보고 같아요, 맞나요?"

| 무엇 | 어떻게 | 왜 이 방식 |
|---|---|---|
| 입력 | `/api/v1/parse` 직후의 SlideDoc (제목·첫 장·마지막 장·글머리 밀도·숫자/표 비율·"결론/제안/Q&A/참고문헌" 같은 장 제목) | 업로드 직후라 발화가 없다. 자료만으로 판단 |
| 1단 (결정론) | 장 제목·키워드 규칙: "참고문헌·연구·실험" → school_project · "가격·출시·고객·기능" → product_launch · "현황·실적·계획·이슈·요청" → work_report · "회고·공유·데모" → casual_peer. 신호가 약하면 미정 | 호출 0, 즉시. 틀려도 사용자가 고친다 |
| 2단 (LLM, 선택) | 1단이 미정일 때만 A.X 1회: 제목 목록 → `{situation, audience, confidence, why}` | 과금 최소 |
| 출력 | `ContextSuggestion {situation, audience, confidence: 0~1, why: "3장 '분기 실적' · 9장 '요청 사항'"}` — `contracts.py` 에 추가, SCHEMA §에 기록 | 계약 없이 dict 로 넘기지 않는다 (DEV_POLICY §4) |
| 화면 (Festa 전 허용 범위) | `#/new` 폼의 상황 선택을 **미리 채우고** 옆에 "자료를 보니 업무 보고 같아요 · 9장 '요청 사항'" 한 줄. 사용자가 바꾸면 그게 이긴다. 새 화면 없음, 바텀시트 없음 | 다크패턴 금지 — 자동으로 확정하지 않는다 |
| 측정 | 동의 세션에서 사용자가 최종 고른 값 vs 추정값 일치율. `build_eval_bundle` 이 같이 내보낸다 | 로드맵 A 와 연결 |

## 2. 내용 제안 — "이 청중은 이걸 기대하는데 자료에 없어요"

페르소나 표(`docs/plan/qa-persona-questions.plan.md`)를 **질문**이 아니라 **빈칸 찾기**에 쓴다. 같은 표, 다른 출력.

| 상황 | 청중이 기대하는 것 (자료에 있어야 할 것) |
|---|---|
| school_project | 문제 정의 · 방법 · 근거/출처 · 결과 수치 · 한계 · 선행 연구 대비 차이 |
| product_launch | 누구의 어떤 문제 · 차별점(비교) · 가격/조건 · 다음 행동(CTA) · 안 되는 경우 |
| work_report | 목표 대비 현황(수치) · 이슈와 원인 · 다음 행동과 기한 · 필요한 자원/결정 요청 · 리스크 |
| casual_peer | 무엇을 만들었나 · 어떻게(구조) · 시행착오 · 재현 방법 · 같이 할 것 |

- 구현: F-06 ConceptDoc + SlideDoc 을 넣고 LLM 1회 — "이 표의 항목 중 자료에 **있는 것/없는 것/약한 것**을 장 번호로 대라. 없는 것을 지어내지 마라."
  결정론 검사: 「있음」으로 답한 항목의 장 번호 본문에 항목 낱말이 실제로 있어야 한다 (graph_eval 의 label_grounded 와 같은 자).
- 출력: `DeckGapDoc {situation, items:[{expect, status: present|weak|missing, slide_nos, why}]}` — F-23 로 번호를 잡고 계약·스키마에 적는다.
- 화면: **Festa 뒤.** 리포트 탭에 「청중이 기대하는 것 5개 중 3개가 자료에 있어요」 + 없는 것 목록. Festa 전에는 `/api/v1/deck-gaps` 만.
- 측정: `graph_eval` 에 `gaps.grounded`(있음 판정의 장 번호가 실제로 맞는 비율) 추가. 사람 채점 10건과 대조.

## 왜 이 순서인가

1. **상황 추정이 먼저** — 페르소나 질문(B3)·내용 제안 둘 다 `situation` 이 맞아야 의미가 있다. 지금은 사용자가 안 고르면 범용이다.
2. 내용 제안은 F-20(구성)과 겹치지 않는다 — F-20 은 "있는 것을 어떻게 배치", 이것은 "없는 것이 무엇".
3. 09-12 실측: 상황 4종으로 재도 질문이 글자까지 같았다. 상황이 파이프라인에 **실제로 작용하게** 만드는 것(B3 페르소나 블록)이 이 둘의 전제다.
