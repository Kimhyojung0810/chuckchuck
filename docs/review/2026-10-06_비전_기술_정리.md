# 척척발표 「비전」 — 무슨 기술이 들어갔나 (2026-10-06)

부스에서 「카메라로 뭘 하는 거예요?」 에 답하기 위한 정리. 코드 기준으로 확인한 사실만 적었다.

## 한 줄 답

> 카메라 영상은 **내 브라우저 안에서만** 분석해요. OpenCV 로 얼굴을 찾아 「정면을 보고 답한 시간」 과 구도 안내를 만들고,
> 발표 중 삐약이 반응은 마이크 소리(말 빠르기 · 크기)로 판단해요. 영상은 서버로 보내지도, 저장하지도 않아요.

## 단계별로 무엇이 무엇을 보나

| 단계 | 입력 | 기술 | 어디서 도나 | 화면에 보이는 것 |
|---|---|---|---|---|
| ① 발표 자료 읽기 | PDF · PPTX | **Upstage Document Parse** (`document-parse`, OCR auto · 도식/차트 enhanced 자동) | 서버 → Upstage API | 장마다 제목 · 본문 · 표 · 차트 설명 → 개념 그래프의 재료 |
| ② 발표 중 삐약이 반응 | **마이크** | Web Audio API 음량(RMS) + 브라우저 음성 인식(Web Speech API) 글자 수 | 브라우저 | 「우웅?」(빠름) 「하암~」(느림) 「잘 안 들려」 「귀가 아파」 「잘 듣고 있어요」 |
| ③ 발표 받아쓰기 · 분석 | 녹음 | SKT **A.X STT** → Upstage **Solar** (개념 · 정합 · 질문) | 서버 | 질문 3개 · 리포트 |
| ④ 질문 화상판 카메라 | **웹캠** | **OpenCV.js** Haar 정면 얼굴 분류기 + 프레임 차분 | 브라우저 **웹 워커** | 「정면 84%」 · 구도 안내(「가운데로 와 주세요」) · 얼굴 테두리 |

카메라 영상 자체를 분석하는 것은 ④뿐이다. ②는 카메라 화면을 바탕으로 깔지만 판단은 소리로 한다 — 「표정 · 시선으로 반응한다」 고 말하면 사실이 아니다.

## ④ 카메라 판단 (OpenCV.js) — `demo/YEHS_demo/js/booth_cv.js` · `booth_cv_worker.js`

**두 가지만 쓴다.**
1. **얼굴 찾기** — Haar Cascade 정면 얼굴 분류기(`haarcascade_frontalface_default.xml`, `detectMultiScale` scale 1.1 · 이웃 4 · 최소 28px).
   정면에 가까운 얼굴만 잡히는 성질을 그대로 쓴다. 그래서 **「정면 n%」 = 이 분류기가 얼굴을 찾은 프레임의 비율**이다 — 추정치를 지어내지 않는다.
2. **움직임** — 가로 80px 로 줄인 흑백 프레임 두 장의 차이(`absdiff → threshold → countNonZero`). 얼굴이 옆을 봐도 사람이 앞에 서 있는지 안다.
   어두운 방(평균 밝기 38 미만)은 센서 잡음이 움직임처럼 보여 움직임 판단을 끈다.

**돌리는 방식**
- 영상을 320px 폭으로 줄여 약 **5.5fps**(180ms 간격, 느린 노트북은 400ms)로 워커에 보낸다. 1~2m 거리 얼굴이 이 폭에서 40px 안팎.
- OpenCV.js(약 10MB, 4.10.0)는 **웹 워커 안에서** 불러온다. 메인 스레드에서 올리면 화면이 2분 넘게 얼었다 → 워커에서 0.7초.
  서버에 사본이 없으면 jsDelivr CDN 에서 받는다. 못 받으면 카메라 판단 없이 질문은 그대로 돈다(카메라는 얹는 층).
- 판단 규칙(순수 함수, 노드 스모크로 시험)
  - 얼굴 가운데가 화면 가장자리 24% 안 → 「화면 가운데로 조금 와 주세요」
  - 얼굴 폭 < 화면의 13% → 「조금 더 가까이」, > 55% → 「조금만 뒤로」
  - 얼굴을 1.2초 못 찾으면 → 「얼굴이 화면 밖에 있어요」
  - 같은 안내가 0.9초 이어질 때만 띄운다(깜빡임 방지)
  - 「정면 n%」 는 20번(약 4초) 이상 쟀을 때만 보여 준다
  - 부스 시작 화면: 얼굴 또는 0.6초 이어진 움직임 → 「사람이 다가왔다」, 4초간 둘 다 없으면 「떠났다」

## ② 말 빠르기 · 크기 (`demo/YEHS_demo/js/vision_cue.js`)

- **크기**: Web Audio `AnalyserNode` 로 마이크 파형의 RMS. 0.03 미만 「잘 안 들려」, 0.22 이상 「귀가 아파」(0.7초 이어질 때).
- **빠르기**: 브라우저 음성 인식이 받아쓴 글자가 늘어난 시점만 「말한 시간」 으로 센 **자/분**. 권장 300~350자/분의 ×1.15 위 「빠름」, ×0.85 아래 「느림」.
  받아쓰기가 없는 브라우저는 음량 봉우리를 음절처럼 세서(초당 7.4 이상 빠름 · 3.2 이하 느림) 대신한다.
- 반응은 1.1초 이어질 때만 바꾼다. 겹치면 큰 소리 > 작은 소리 > 빠름 > 느림.

## 개인정보 — 말할 수 있는 것 / 정확히 해야 할 것

- **카메라 영상**: 브라우저 밖으로 안 나간다. 워커 안에서 판단하고 결과(얼굴 상자 · 움직임 비율)만 화면에 쓴다. 저장 안 함. 화면 문구 「영상은 이 화면에만 보여요 · 저장하지 않아요」 와 일치.
- **녹음**: 질문을 만들려면 서버로 간다(A.X STT · Solar). 「아무것도 안 보내요」 라고 하면 틀린 말이다.
- **실시간 받아쓰기(②의 글자 수)**: 크롬의 Web Speech API 는 브라우저 구현에 따라 음성을 브라우저 회사(구글) 서버에서 인식한다. 「완전히 기기 안」 이라고 하지 않는다.
- 부스 녹음 체험은 미리 준비한 발표 녹음(덱마다 2개)을 쓴다 — 발표 녹음은 직접 발표를 고른 경우에만 생긴다.
- 질문에 말로 답하면 받아쓴 **글**이 판정을 위해 서버(Solar)로 간다.

## 부스에서 30초 설명

1. 「발표 자료는 Upstage Document Parse 로 읽어서, 장마다 무슨 주장과 근거가 있는지 그래프로 만들어요.」
2. 「발표하는 동안 삐약이는 말 빠르기와 목소리 크기에 반응해요. 이건 마이크로 판단해요.」
3. 「질문에 답할 때는 카메라로 얼굴이 정면에 있는지 봐요. OpenCV 얼굴 찾기를 브라우저 안에서 돌려서, 영상은 서버로 안 가요. 끝나면 정면으로 답한 시간이 몇 %였는지 보여 줘요.」
4. 「답은 Solar 가 자료와 대조해서 판정하고, 부족하면 어디가 빠졌는지 되물어요.」

## 한계 (물으면 솔직하게)

- Haar 분류기는 2001년 Viola-Jones 계열의 고전 기법이다. 고개를 돌리거나 조명이 어두우면 놓친다 — 그래서 「정면 비율」 로만 쓰고 시선 추적이라고 하지 않는다.
- 표정 · 감정 · 시선 방향은 보지 않는다.
- 삐약이 반응은 말 빠르기 · 크기 두 가지뿐이다. 내용 판단은 발표가 끝난 뒤 서버 분석에서 한다.
