# QA 질문이 지엽적인 원인 분석 (2026-09-28)

> 요청: "PPT·음성 → concept graph → 위계에 따라 의미 있는 개념부터 질문" 이 실제로 동작하는지, 왜 질문이 지엽적인지 원인 파악.
> 이 문서는 조사하면서 과정을 계속 덧붙인다. 근거는 [코드]/[실측]/[판단] 으로 구분.

## 0. 가설 (조사 시작 전)

- H1. concept graph 가 아예 질문 생성에 안 들어간다 (다른 입력 — 슬라이드 텍스트·전사 — 만 씀).
- H2. 그래프는 들어가지만 "위계(중요도)" 를 안 쓰고, 슬라이드 순서·무작위·첫 N개로 개념을 고른다.
- H3. 그래프 자체가 위계가 없다 (노드 중요도/계층 필드가 비었거나 다 같음).
- H4. 위계는 쓰지만 후처리(중복 제거·근거 검사·전제 차단 등 최근 방어 코드)가 큰 개념 질문을 버리고 세부 질문만 남긴다.
- H5. 프롬프트가 "슬라이드 근거 문장을 인용하라" 류로 강하게 묶어서 LLM 이 세부 사실 질문으로 몰린다.

## 1. 진행 로그

### 1-1. 파이프라인 경로 확인 [코드]

`F-07 build_graph`(chuckchuck/f07_graph.py) → `F-08 triage_questions` → `build_questions`(chuckchuck/f08_questions.py).
**그래프는 질문 생성에 실제로 들어간다** → H1 기각. 문제는 "들어가서 어떻게 쓰이느냐" 다.

그래프가 질문 순위에 영향을 주는 경로는 딱 셋:
1. `node.weight` — 후보 정렬 키 (`_ordered_candidates`, `_rerank`)
2. `sections[].slide_role` — 표지·맺음말 개념 강등 (`_role_rank_of`)
3. `neighbors_of` — 이웃끼리 연달아 묻지 않게 강등 (`_spread_adjacent`)
+ 프롬프트에 parent 경로·이웃을 **설명용 문맥**으로 실음 (`_relation_line`).

**위계(parent/depth/자식 수) 자체는 순위 키에 없다.** 위계가 순위에 닿는 유일한 길은
f07 `_raw_weight` 의 깊이 감점 `0.05 × (depth-1)` 하나다.

### 1-2. weight 가 뜻하는 것 [코드]

`f07_graph.py:_raw_weight` — weight = 0.18·importance + 0.30·장 비율 + 0.25·글자 비율 + 0.10·그림 + 0.12·개념목록 언급 + 0.05·제목 적중 − 0.05·(depth−1).
→ **"자료에서 이 개념이 적힌 장이 얼마나 많고 글자가 얼마나 빽빽한가"** 다. "발표의 뼈대인가" 가 아니다.
- 부모 개념이 자식들의 비중을 물려받지 않는다(서브트리 합산 없음). 자식 11개를 거느린 허브도 자기 `slide_nos` 만큼만 받는다.
- 결론 장 1장에만 적힌 주장(예: "수면의 질 = 시간×연속성×규칙성")은 글자 많은 설명 장의 세부 용어보다 낮게 나온다.

### 1-7. 질문 문장이 지엽적으로 읽히는 부가 요인 [코드]+[실측]

- **질문 1개 = 개념 1개 = 그 개념의 근거 장(최대 3장) 본문.** `answer_gist` 는 "그 장 본문에 있는 말로만" 쓰게 강제된다
  (`QUESTION_SYSTEM_PROMPT`, `SLIDE_BODY_MAX`). 그래서 잎 개념이 뽑히면 답이 "기억 정리·감정 처리" 같은 **사실 확인**이 된다.
  여러 장을 가로지르는 질문("세 요소 중 왜 연속성을 따로 강조했나", "주말 몰아자기가 공식의 어느 항을 깨나")을 만들 틀이 없다.
- **문헌(F-24)이 기본으로 켜져 있고**, 문헌 줄이 붙은 개념은 인용이 없으면 `qa-cite` 로 **강제로 다시 쓴다.**
  9/26 녹음 실행: 7개 중 6개가 "Lim et al. (2013)는 수면 분절이 …했는데, 발표에서 〈세부 사실〉했어요" 틀(같은 논문 5회).
  검색 논문 하나가 여러 노드에 붙으면서 질문이 **같은 틀 + 세부 사실 대조**로 획일화된다. 지엽감을 키우는 요인이지만 근본 원인은 아니다.
- 녹음 경로에서는 `source`(모순 > 누락 > 덜 말함 > 흐름 > 자료 비중)가 **모든 정렬 키 위**다. 잘 설명한 주제 개념은
  `core_weight` 로 맨 뒤 그룹이고, 누락된 잎(weight ≥ 0.2)이 먼저 나온다 — 리포트와 맞추려는 의도된 설계지만 위계와는 무관하게 돈다.

## 3. 고칠 방향 (제안 — 아직 코드 안 건드림)

우선순위 순. 1·2 는 같이 가야 효과가 난다 (1-6).

1. **F-07 루트 클램프를 글자 weight 로 고르지 않기** — LLM 이 준 parent 구조를 존중: 루트 후보를 "서브트리 크기·서브트리가 덮는 장 수" 로 순위 매겨 남긴다.
   강등 대상도 "자식이 없는 작은 루트" 부터. (`f07_graph.py:_clamp_roots`)
2. **F-08 후보 정렬에 위계 키 추가** — (자료만 경로 기준) `depth` → 서브트리 장 범위 → weight. 또는 weight 에 서브트리 합산을 넣어 부모가 자식보다 가볍지 않게.
   `_spread_adjacent` 는 "자식이 먼저 뽑혔으면 부모 강등" 이 아니라 **부모 먼저, 같은 부모 밑 형제는 하나만** 으로.
3. **`CANDIDATE_LIMIT` 창을 weight 가 아닌 위계로 채우기** — 최소한 루트·depth1 은 창에 무조건 넣는다.
4. **트랙별 질문 배합** — 5분 트랙 3문항이면 예: 루트(주제) 1 · 주제↔하위 연결 1 · 약점(누락·모순) 1. 1분 트랙은 루트.
   루트 질문은 답의 골자를 서브트리 장 전체 본문에서 쓰게 해 "가로지르는 질문" 이 가능하게.
5. **문헌 강제 재작성 완화** — 트랙당 인용 질문 상한(예: 5분 1개), 같은 논문 재사용 금지.
6. (측정) `labs/qa_lab` 에 "루트/주제 개념이 상위 N 에 있는가" 표식 추가 → 고친 뒤 회귀 확인.

녹음 경로(source 우선)는 리포트 일치 규칙이 걸려 있어 팀 합의가 필요 — 예: "누락은 그 개념이 depth ≤ 1 일 때만 최상위" 같은 절충.
