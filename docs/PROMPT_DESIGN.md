# 척척발표 — 프롬프트 설계·튜닝

이 문서는 척척발표의 LLM 프롬프트를 어떤 원칙으로 설계했고, 실제로 어떤 문제를 겪은 뒤
어떻게 튜닝했는지 정리한다. 프롬프트 원문은 각 모듈(`chuckchuck/f06~f20_*.py`)의
`SYSTEM_PROMPT` 상수가 단일 원본이며, 이 문서와 코드가 어긋나면 코드가 맞다.
공통 인프라는 `chuckchuck/_json_text.py`(JSON 복구)와
`chuckchuck/providers/llm_impl.py`(`OpenAICompatLLM.complete`)에 있다.

## 1. 공통 설계 원칙

모든 모듈이 지키는 규칙 세 가지가 있다 — 코드 리뷰가 아니라 실제로 틀린 응답을 겪고 나서
못 박은 것들이다.

1. **"자료에 없는 내용을 지어내지 마라"를 모든 시스템 프롬프트에 반복한다.** F-06(개념
   추출)·F-11(정합 판정)·F-14(채점)·F-12(청중 수다) 전부 이 문장이 있다. LLM이 근거 없이
   숫자·개념·인용을 만들어내는 걸 프롬프트 단계에서부터 막는다.
2. **출력 스키마를 프롬프트 안에 JSON 예시로 박아 넣는다.** "적절한 형식으로 답하라" 대신
   실제 키·값 예시를 통째로 준다. 스키마 밖의 필드는 코드가 버린다.
3. **"코드펜스·주석·말머리 없이 JSON 객체 하나만 출력하라"를 매번 명시한다.** 그래도 안
   지켜지는 경우가 있어 §2의 복구 인프라가 따로 있다.

## 2. JSON 강제·복구 인프라

프롬프트 지시만으로는 항상 순수 JSON이 나오지 않는다. 세 겹의 방어가 있다.

### 2-1. API 레벨 강제 (`OpenAICompatLLM.complete`, `json_mode=True`)

```python
payload["response_format"] = {"type": "json_object"}
```

Upstage 계열은 이것만으로 부족하다 — **`messages` 안에 문자열 `"json"`이 실제로 있어야
하고 없으면 400을 던진다.** 이 지뢰는 F-09 답변 판정에서 "모르겠어요"류 답변을 처리하다
실제로 걸렸고, 지금은 `complete()`가 시스템 프롬프트에 "json"이 없으면 자동으로 한 줄을
덧붙여 방어한다.

```python
if "json" not in f"{system}\n{user}".lower():
    payload["messages"][0]["content"] += "\n\n출력은 JSON 객체 하나로만 한다."
```

### 2-2. 텍스트 복구 (`_json_text.repair_json_text` / `extract_json_object`)

코드펜스 제거 → trailing comma 제거 → 잘린 괄호 보정(마지막 완전한 `}`까지만 남기거나
부족한 닫는 괄호를 채움) → 그래도 안 되면 정규식으로 가장 바깥 `{...}`만 추출. 실패해도
예외를 던지지 않고 "최선의 결과"를 반환하며, 최종 실패 시 원문은 서버 로그에만 남기고
사용자 화면에는 앞 200자만 보여준다 — "이 실패를 화면 문구만 보고 역추적하느라 고생한
적이 있다"는 주석이 그 이유를 말해준다.

### 2-3. 재요청 넛지 (모듈별 `JSON_RETRY_NUDGE`)

복구도 실패하면 시스템 프롬프트에 넛지 문구를 덧붙여 **한 번만** 더 묻는다
(F-11·F-14 등: `for nudge in ("", JSON_RETRY_NUDGE): ...`). F-11에는 JSON은
파싱됐지만 `items`가 통째로 비어 돌아온 경우를 위한 `EMPTY_RETRY_NUDGE`도 따로 있다 —
파싱 성공과 "쓸모 있는 응답"은 다른 실패 축이라는 걸 반영한 설계다.

## 3. 모듈별 설계·튜닝 사례

### 3-1. F-06 개념 추출 — 배치·클리핑으로 잘림 방지

`SYSTEM_PROMPT`(`f06_concepts.py`)는 슬라이드별 `topic/keywords/concepts/importance`를
뽑되 "부모-자식 관계는 만들지 마라"(그건 F-07 몫)로 책임을 명확히 자른다. 슬라이드를
한 번에 다 넣으면 응답이 잘려 `ConceptError`가 나서, `BATCH_SIZE`(기본 8)로 나누고
슬라이드 본문을 `MAX_SLIDE_CHARS`(기본 1200자)로 클리핑한다. 둘 다 환경변수로 튜닝
가능하다 — 자료가 큰 데모 리허설에서 실측하며 값을 맞췄다.

### 3-2. F-07/F-11 — 프롬프트 안에서 "판정 대상"을 먼저 배치

F-11 정합 판정(`f11_align.py`)의 `_build_user_prompt`는 개념 목록(판정 대상)을 슬라이드별
발화보다 **앞에** 둔다. 주석에 그 이유가 남아 있다: "F-07 실측 교훈의 재적용 — 판정
대상(개념)을 앞에 둬야 모델이 발화를 개념에 매핑하지, 발화를 새 개념으로 다시 뽑지
않는다." 즉 같은 정보라도 **프롬프트 안의 순서**가 모델이 태스크를 뭘로 이해하는지를
바꾼다는 걸 실측으로 확인하고 F-07에서 F-11로 그대로 재적용한 사례다.

`verdict`는 `aligned`/`justified_skip`/`missing`/`contradiction` 4종으로 못 박고,
"aligned·contradiction은 evidence가 필수 — 근거 없는 모순 판정은 버려진다"처럼 **판정
종류별로 근거 요구 수준을 다르게** 건다.

**튜닝 사고 사례 — `MENTION_MIN`.** "개념이 발화에 몇 번 언급돼야 '설명함'으로 인정할지"
임계값을 2에서 5로 올렸다. 2였을 때 LLM이 '누락'이라 판정해도 코드가 단어가 두 번
나왔다는 이유만으로 '설명함'으로 뒤집어, 2026-08-10 실측에서 개념 18개 중 누락이
0개로 나오는 사고가 있었다. "심사위원이 후한 판정을 눈치채면 리포트 전체의 신뢰가 같이
무너진다"는 게 이 값을 시연 직전에도 조일 수 있게 환경변수로 뺀 이유다.

### 3-3. F-09 답변 코칭 — 소크라테스식 3단계 프롬프트

`COACH_SYSTEM_PROMPT`는 사용자가 답변에 막혔을 때 쓰는 프롬프트로, 단계별로 완전히
다른 지시를 준다.

| 단계 | 지시 | 금지 |
|---|---|---|
| `narrow` | 원래 질문보다 훨씬 쉬운 되물음 하나(예/아니오·한 단어로 답 가능) | 답을 알려주는 것 |
| `explain` | 기대하는 답의 골자+근거 슬라이드+실제 발화를 엮어 설명 | 자료에 없는 사실 지어내기 |
| `clarify` | **같은 질문**을 더 쉬운 말로 다시 씀(질문 대상 자체는 안 바꿈) | 발표자 탓으로 돌리는 반응 |

"절대 나무라지 마라. 한 문장으로 안심시키고 바로 도움으로 넘어간다"는 공통 지시가
맨 앞에 있다 — 코칭이 지적처럼 읽히지 않게 톤을 먼저 건다.

### 3-4. F-12 청중 수다 — "코드가 사실을 고르고 LLM은 말투만 입힌다"

F-12가 다른 모듈과 가장 다른 지점은 **LLM에게 뭘 말할지 정하는 권한을 주지 않는다**는
것이다. 언급할 사실(누락/모순/자료-발화 갭)은 결정적 코드(`_midm_points` 등)가 정합
데이터에서 골라 정렬하고, LLM은 그 사실 하나에 캐릭터 말투만 입힌다. 모델 4개(믿:음·
쏠라·엑사원·에이닷)는 파이프라인에서 실제로 한 일을 그대로 성격으로 번역했다 — 믿:음은
정합 판정을 하니 "어긋난 곳을 못 지나가는" 성격, 쏠라는 문서 전체를 읽으니 "순서·구조를
보는" 성격, 에이닷은 STT를 담당하니 "들은 것 얘기를 하는" 성격.

`TONE_GUIDE`는 규칙 나열에 그치지 않고 **대비 예시**를 직접 프롬프트에 넣는다:

```
너무 뭉뚱그림(버려짐): "그거 더 듣고 싶었는데!"
좋음: "3번 장 'Contrastive Learning', 왜 쓰는지가 안 나왔어. 한 줄만 붙여줘도 확 붙을 텐데!"
```

규칙 중 "슬라이드 번호는 사실에 적혀 있을 때만 말하라"·"발표자의 실제 발화를 인용할 땐
큰따옴표로"는 프론트가 그 번호/인용을 UI 요소(슬라이드 링크, 대본 조각)로 다시 쓰기
때문에 형식을 어기면 화면이 깨진다 — 프롬프트 규칙이 UI 계약과 묶여 있다.

**프롬프트만으로 안 끝난다 — 코드 레벨 후처리 필터가 한 겹 더 있다.** `TONE_GUIDE`에
"발표자의 목소리·발음·외모·성격·재능을 평가하는 말은 절대 금지"라고 써도, 응답에
`BANNED_PATTERNS`(`"목소리", "발음", "외모", "못생", "바보"` 등)가 매치되면 그 대사를
통째로 버린다. 프롬프트 지시 하나만 믿지 않는 이중 방어다.

### 3-5. F-14 채점표 — "모르겠다"를 0점과 분리

`SYSTEM_PROMPT`(`f14_rubric.py`)는 점수 구간을 명시(90~100/70~89/40~69/1~39/0)한 뒤
**"판단할 근거가 자료에 없으면 그 번호를 결과에서 아예 빼라. 0점은 '안 했다'는 판정이지
'모르겠다'가 아니다"**를 강조한다. 채점 항목마다 서로 다른 근거를 요구해("같은 문장을
모든 항목에 붙이지 마라") 근거 재활용으로 점수를 부풀리는 걸 막는다. 집계 로직(클러스터
가중평균)은 순수 함수로 완전히 분리돼 있어 LLM은 항목 점수만 내고 최종 점수 계산에는
관여하지 않는다.

## 4. 파인튜닝 쪽 프롬프트/타깃 설계 (F-18, `20_AIHub_data`)

서비스 프롬프트와 다른 층이지만 같은 원칙(스키마 강제·태스크 분리)이 적용됐다.
자세한 데이터 맥락은 [`docs/DATA_PIPELINE.md`](DATA_PIPELINE.md) §2-2·2-3 참고.

- **타깃 포맷을 `태그<TAB>원문구간` 줄 목록으로 고정**(`20_AIHub_data/src/prompt.py`).
  자유서술 대신 이 포맷을 쓴 이유는 파싱이 결정적이고, 스팬 단위 P/R/F1이 그대로
  나오기 때문이다. 없으면 `NONE` 한 줄만 출력하게 해 빈 응답과 "찾을 게 없음"을
  구분한다.
- **통합 프롬프트 → 태그별 전용 프롬프트로 분리**(`single_tag_system(tag)`). REP·FIL·WR을
  한 프롬프트로 동시에 시키면 최적 디코딩 조건이 태그마다 배타적이라는 걸 실측으로
  확인한 뒤(REP는 무보정 greedy가 최적, FIL은 `repetition_penalty`가 있어야 좋아짐),
  프롬프트 자체를 태그 하나만 묻도록 쪼갰다.

## 5. 튜닝 손잡이 (환경변수)

| 변수 | 기본값 | 모듈 | 의미 |
|---|---|---|---|
| `CHUCKCHUCK_CONCEPT_BATCH_SIZE` | 8 | F-06 | 한 번에 넣는 슬라이드 수 — 크면 응답 잘림 |
| `CHUCKCHUCK_CONCEPT_MAX_SLIDE_CHARS` | 1200 | F-06 | 슬라이드 본문 클리핑 길이 |
| `CHUCKCHUCK_CONCEPT_MAX_WORKERS` | 4 | F-06 | 배치 동시 호출 수 — 크면 레이트리밋 |
| `CHUCKCHUCK_ALIGN_MENTION_MIN` | 5 | F-11 | 몇 번 언급돼야 "설명함"으로 인정할지 (§3-2 사고 이후 2→5) |

## 6. 실패에서 나온 설계 결정 요약

| 겪은 문제 | 원인 | 조치 |
|---|---|---|
| F-09 "모르겠어요" 처리 중 Upstage 400 | `json_mode`는 켰지만 프롬프트에 "json" 낱말이 없었음 | `complete()`가 자동으로 "json" 문구 삽입 |
| F-11 개념 18개 중 누락 0개(2026-08-10) | `MENTION_MIN=2`가 너무 후해 언급만 해도 '설명함'으로 뒤집힘 | 5로 상향 + 환경변수화 |
| F-07 개념 그래프에서 발화가 새 개념으로 오인식 | 판정 대상을 발화 뒤에 배치 | 판정 대상을 프롬프트 앞쪽으로 이동, F-11에도 재적용 |
| F-12 캐릭터가 외모·발음을 평가하는 대사 생성 | 프롬프트 지시만으로는 100% 안 지켜짐 | `BANNED_PATTERNS` 코드 레벨 필터 추가 |
| F-06 큰 자료에서 JSON 잘림 | 슬라이드 전체를 한 번에 요청 | 배치 분할 + 슬라이드 클리핑 |
| F-18 통합 태거에서 FIL이 베이스보다 퇴행 | REP·FIL·WR 최적 디코딩 조건이 배타적 | 태그별 프롬프트·데이터셋·어댑터 분리 |
