## 먼저 알아야 할 것 (콜드 스타트용)

```bash

DEMO_PORT=8799 ./demo/run_bridge_midm.sh

# 회귀 기준선
python -m pytest tests/ -q     # 591 passed · 7 skipped
```

- **파이썬을 고쳤으면 브리지를 재기동해야 검증이 된다.** 파이썬은 임포트 시점에
  메모리로 올라간다. JS/CSS 는 매 요청 디스크에서 읽어 즉시 반영된다.
  재기동 후 첫 요청은 22GB 로드로 2~3분 — 반드시 예열한다.
- **`pkill -f "python -m demo.bridge"` 를 쓰지 마라.** 명령줄이 패턴과 일치해서
  **자기 셸까지 죽인다.** keepalive 가 물고 있으므로 그냥 두거나 PID 로 집는다.
- **`js/*.js` · `css/*.css` 를 고쳤으면 `index.html` 의 `?v=` 를 올린다.** 현재 `qg5`.
  안 올리면 브라우저가 옛 파일을 서빙해서 "고쳤는데 안 바뀐다" 가 된다.
- **프론트 JS 자동 테스트는 0개다.** `tests/` 23개가 전부 파이썬이다. JS 를 고쳤으면
  `node --check` 로 문법만 보고, 동작은 사람이 눌러야 확인된다.

## 1. 힌트 분모가 질문 도중에 줄어든다 🟢 **여기서 시작**

**크기** 작음 (~20분) · **위험** 낮음 · **JS 만**

**증상**: 한 질문 안에서 말풍선이 "힌트 2/**4**" 를 냈다가 다음에 "힌트 3/**3**" 을 낸다.

**원인**: `liveHints()`(`qa_live.js:1186`) 가 **직전에 보여준 길이가 아니라 `built`
와 비교**한다.

```js
function liveHints() {
  const judged = (qa.live.lastJudgement && qa.live.lastJudgement.hints) || [];
  const built = liveQuestionHints();          // qa_live.js:1198 — 길이 고정
  return judged.length >= built.length ? judged : built;
}
```

판정 사다리(`judged`)는 턴마다 바뀐다. 4단이던 것이 3단으로 오면
`judged.length >= built.length` 가 여전히 참이라 3단짜리를 돌려준다 → 분모가 준다.
**자기 docstring 의 의도("짧은 쪽으로 내려가면 소비한 인덱스가 무효가 된다")를
못 지키는 자리다.**

**고치는 법**: 이 질문에서 **본 최대 길이**를 상태에 남기고 줄어들지 않게 한다.

- `qa.live` 에 `hintTotal: 0` 을 더한다 (상태 초기화는 `newLiveState`)
- `liveHints()` 가 고른 목록의 길이가 `L.hintTotal` 보다 크면 갱신하고,
  말풍선에 싣는 `total`(`qa_live.js:476`)은 `L.hintTotal` 을 쓴다
- **질문이 바뀔 때 0 으로 되돌린다** — `L.hintLevel = 0` 과 같은 지점(`qa_live.js:1086`)

**검증**: `node --check demo/YEHS_demo/js/qa_live.js` → `?v=` 올리기 → 한 질문에서
힌트를 두 번 이상 열어 분모가 안 줄어드는지 눈으로.

**주의**: 기능 영향은 없다. `liveStalled()` 는 길이가 고정된 `liveQuestionHints()`
를 보므로 출구 판단은 이 변경과 무관하다. **순수 표시 문제다.**

## 3. 5분 트랙에서 질문 3개의 모범답이 사실상 같다 🟡

**크기** 중간 · **위험** 중간(멀쩡한 질문을 떨어뜨릴 수 있음) · **파이썬**

**증상**: 5분 트랙에서 한 번 제대로 답하면 **세 질문이 전부 good 85 로 닫힌다.**
사용자가 "정답 판정이 너무 광범위하다" 고 느낀 실체가 이것이다 — 판정이 무른 게
아니라 **질문이 같아서** 아무 답이나 맞는 것처럼 보인다 (측정: 정산 문서 §W3).

**왜 5분에서만**: `QA_TRACK_LIMITS = {"1":1, "5":3, "10":7}`(`contracts.py:1321`).
5분은 후보 13개 중 **가장 중심적인(=서로 답이 겹치는) 상위 3개**만 뽑는다.
10분은 뒤쪽 후보까지 내려가 골자가 흩어진다 (0.40 넘게 겹치는 쌍이 21개 중 1개).

**왜 기존 방어가 안 먹었나**: `_spread_adjacent`(`f08_questions.py:642`) 가 정확히
이걸 막으려고 있는데 **인접을 `graph.edges` 로만 본다.** 문제의 세 노드 사이엔
간선이 하나도 없어서 강등이 한 번도 발동하지 않았다.

**고치는 법**: `_spread_adjacent` 를 고치지 말고 **질문을 받아 온 뒤**에 건다 —
`_normalize_questions`(`f08_questions.py:969`) 결과에서 `answer_gist` 토큰 겹침
(Jaccard, **LLM 없이 결정적으로**)이 임계 이상인 쌍을 찾아 하나만 남기고
`deferred` 에서 승격한다. 이 모듈의 원칙("무엇을 물을지는 코드가 정하고 LLM 은
문장만 쓴다")과 같은 결이다.

**임계 정하는 법**: 실측한 값이 있다. 10분 트랙 21쌍 중 0.41 이 최대였고 그 다음이
0.31 이다. **0.40 을 넘는 쌍만 잡으면 10분 트랙은 사실상 안 건드린다.**

**검증**: `examples/qa_judge_probe.py` 가 이미 골자 쌍별 겹침을 재는 코드를 갖고
있다. 5분 트랙으로 뽑아 중복이 사라지는지, 10분 트랙 질문 수가 7개로 유지되는지.

**급하지 않은 이유**: 시연은 10분 기본 트랙으로 한다 — 그것이 오늘의 답이었다.

## 4. 모범답이 자료에 없는 지식으로 살을 붙인다 🔴 크지만 제일 값어치 있음

**크기** 큼 · **위험** 높음(F-08 계약·프롬프트 길이·과금) · **마감 뒤 과제**

**증상**: 자료엔 "약 90–110분" 만 있는데 모범답이 "**뇌파 측정을 통해** 입증되었으며"
라고 쓴다. 심사에서 지적당하면 방어할 말이 없다.

**시도했다가 기각된 설계 — 반복하지 마라**: 모범답을 자료와 대조해 **겹침이 낮으면
버리는** 방식. 측정이 신호가 거꾸로임을 보여줬다.

| 모범답 | 성격 | 자료 겹침 |
|---|---|---|
| 깊은 수면 | 좋은 답 | 9% |
| 수면 질 | 좋은 답 | 10% |
| 수면 주기 | 「뇌파」 살붙임 ⚠ | **24%** |
| 회복한 시간 | 발판 유출 ⚠ | 0% |

바닥값을 두면 **좋은 답 둘을 버리고 살붙인 답을 통과**시킨다.

**왜 그런가 — 이것이 진짜 원인**: **F-08 이 `SlideDoc` 을 아예 안 받는다.**
`ConceptGraph` 의 짧은 요약(예: `deep-sleep.summary = "신체 회복 담당, 초반에 발생"`
= 토큰 9개)만 쥐고 있어서, 제대로 풀어 쓴 답일수록 겹침이 낮아진다.

**제대로 된 해법**: `SlideDoc`(또는 근거 장의 본문)을 F-08 까지 내린다. 그러면
겹침 대조가 비로소 의미를 갖고, 프롬프트도 "자료에 있는 말로만 써라" 를 **강제**할
근거가 생긴다.

**주의**: 프롬프트가 길어지면 과금과 지연이 는다. 노드의 `slide_nos` 로 **근거 장만**
잘라 넣는 것이 현실적이다 (`node.slide_nos` 는 이미 있다 — `f08_questions.py:1017`).
