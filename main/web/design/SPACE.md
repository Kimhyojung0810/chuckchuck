# SPACE — 3D 공간 설계

> 방 하나, 정거장 넷, 몸을 돌리듯 90°. 조작은 버튼뿐이다. (BRIEF §2)

## 1. 방

정사각형 방 하나의 한가운데에 사용자가 서 있다. 벽 네 면이 각각 한 단계의 「정거장」 이다.

```
                 ┌──────────── 벽 0 ────────────┐
                 │      ① 자료 올리기 (0°)       │
                 │                               │
        벽 270°  │  ④ 리포트        ② 발표       │  벽 90°
                 │   (270°)    ●     (90°)       │
                 │           사용자               │
                 │      ③ 질의응답 (180°)        │
                 └──────────── 벽 180 ───────────┘
              다음 단계 = 오른쪽으로 90° (시계 방향)
```

- **건축은 하나.** 네 벽은 같은 재질 · 같은 높이 · 같은 몰딩이다. 차이는 그 벽을 비추는 **조명**뿐이다.
- **재질.** 벽은 따뜻한 회색 미장(먹에 가까운 `#1d1c19` ~ 조명 받은 `#3a362f`), 바닥은 어둡게 광택 있는 콘크리트(정면 조명이 길게 비친다), 천장은 어둡다.
- **이어지는 요소 둘.** 천장 바로 밑을 한 바퀴 도는 간접 조명 줄(코브 라이트) · 바닥과 벽이 만나는 그림자 선. 돌 때 이 두 줄이 이어져 보여서 「같은 방」 이 된다.
- **장식 없음.** 소품 · 가구 · 창밖 풍경 없음. 모서리의 그늘과 빛 웅덩이로만 깊이를 만든다.

## 2. 시점 (카메라)

| 정거장 | 방향(yaw) | 들어오는 버튼 예 |
|---|---|---|
| ① 자료 올리기 | 0° | 첫 화면 · 「새 리허설」 |
| ② 발표 | 90° | 「발표 시작하기」 |
| ③ 질의응답 | 180° | 「질문 받으러 가기」 |
| ④ 리포트 | 270° | 「리포트 보기」 |

- **한 방향으로만 돈다.** 앞 단계 → 다음 단계는 언제나 오른쪽으로 +90°. 리포트에서 「새 리허설」 이면 270° → 360° 로 계속 돈다 (각도를 0 으로 되감지 않는다 — 거꾸로 270° 를 휙 도는 일이 없게).
- **뒤로 가기**(브라우저 · 「이전」)는 왼쪽으로 −90°. 두 칸 이상 건너뛰면(단계 표시에서 고르기) 최단 방향으로 돈다.
- **사용자는 시점을 직접 움직이지 않는다.** 마우스 드래그 · 스크롤 · 방향키로 돌지 않는다 (발표 중 ←/→ 는 슬라이드 넘김이다).

### 전환 한 번의 모양

```
시간   0 ───────── 0.5 ───────── 1
회전   ▁▂▃▅▆▇█  (in-out, 0 → 90°)
물러섬 ▁▃▅▇▅▃▁  (한 걸음 뒤로 갔다가 다시 다가감, 최대 0.16 × 창 거리)
떠나는 창   ██▆▃▁        (0~45% 동안 사라짐, 살짝 작아짐)
오는 창          ▁▃▆██  (50~100% 동안 나타남)
조명   현재 정거장 값 → 다음 정거장 값 (회전과 같은 곡선)
```

- 길이: 데스크톱 1.1s · 폰 0.9s. 곡선 `cubic-bezier(.65, 0, .35, 1)`.
- 「한 걸음 물러섬」 이 있어야 고개만 돌린 게 아니라 몸을 돌린 느낌이 난다 — 빼지 않는다.
- 전환 중에는 입력을 받지 않는다(두 번 누름 방지). 전환은 끊지 않고 끝까지 간다.
- **움직임 줄이기**(`prefers-reduced-motion`)면 회전 · 물러섬 없이 0.2s 겹쳐 바뀌기. 조명도 바로 바뀐다.

## 3. 조명 — 단계마다

같은 방에 조명만 다르다. 값은 CSS 변수 몇 개(벽 밝기 · 색 · 바닥 빛 웅덩이 · 코브 라이트 세기)로, 전환 동안 사이값을 지난다.

| 정거장 | 느낌 | 벽 밝기 | 빛 색 | 바닥 빛 웅덩이 | 코브 라이트 |
|---|---|---|---|---|---|
| ① 자료 올리기 | 아침 작업실 — 고르고 맑음 | 중간 (.55) | 중립 미색 `#E8E4DC` | 넓고 옅게 | 켬 |
| ② 발표 | 무대 — 주변이 가라앉고 정면만 | 낮음 (.22) | 금빛 `#C9A96E` | 좁고 진하게(스포트) | 거의 끔 |
| ③ 질의응답 | 마주 앉은 대화 — 따뜻하고 낮게 | 중간 낮음 (.38) | 따뜻한 `#D9B98A` | 둥글게 둘 | 은은 |
| ④ 리포트 | 읽는 방 — 가장 밝고 고르게 | 높음 (.72) | 맑은 미색 `#F2EDE4` | 넓게 | 켬 |

## 4. 3D 와 2D 의 경계

| 3D (공간) | 2D (창 안) |
|---|---|
| 방 · 벽 · 바닥 · 천장 · 조명 | 자료(PPT) · 텍스트 입력 · 질문 · 판정 · 점수 · 상세 리포트 |
| 시점 회전 · 물러섬 | 버튼 · 폼 · 목록 |
| (다음 단계) 발표 무대 연출 · 개념 그래프 같은 개념 시각화 | 카메라 화면(발표 · Q&A) — **지금 그대로** |

- **떠 있는 창**(visionOS 의 window): 정거장마다 정면에 창 하나. 모서리 24px · 1px 밝은 테두리 · 아래로 떨어지는 부드러운 그림자(공중에 떠 있음) · 바닥에 비친 옅은 반사. **유리(backdrop blur) 없음** — 토스 규율. 대신 불투명에 가까운 면(무대 `#121210` 92%)을 쓴다. 리포트 창만 종이(`--paper`).
- 창은 정확히 **원근 거리(perspective)** 에 놓는다 → 멈춰 있을 때 화면 평면과 겹쳐 1:1 로 그려진다 (글자가 흐려지거나 커지지 않는다).

## 5. 구현 방식

### 5-1. 왜 CSS 3D 인가 (Three.js 가 아니라)

- 창 안은 진짜 DOM 이어야 한다 — 입력칸 · 선택 · 화면 읽기 · 카메라 `<video>` · 기존 화면 코드. CSS 3D 는 DOM 을 그대로 3D 에 놓는다.
- 방은 평면 여섯 장(벽 넷 · 바닥 · 천장)과 그라디언트면 된다 — 3D 엔진이 필요 없다. 내려받을 것도 없다.
- 개념 시각화처럼 진짜 3D 가 필요한 곳만 그 창 안에서 Three.js(이미 `js/vendor/3d-force-graph`)를 쓴다.

### 5-2. 구조

```
.studio                      perspective: P   (화면 전체, 2D HUD 는 이 밖)
  .studio-world              transform: translateZ(P − dolly) rotateY(yaw)   ← 카메라
    .room-wall[data-at=0..3] rotateY(k·90°) translateZ(−R)   ← 벽 (R > P)
    .room-floor / .room-ceiling   rotateX(±90°) …
    .station[data-at=k]      rotateY(k·90°) translateZ(−P)   ← 떠 있는 창 (멈추면 1:1)
.studio-hud                  2D — 상단바 · 단계 표시 · 알림 (3D 밖, 흔들리지 않음)
```

- **카메라 뒤로 넘어간 면은 그리지 않는다** (1차 구현에서 확인). CSS 원근은 카메라 뒤(z > 0)에 걸친 면을 뒤집어 그려 화면을 덮는다 — 멈춰 있을 때 옆 벽의 뒤쪽 절반 · 바닥 · 천장의 뒤쪽 절반이 위아래 띠로 나타났다. 그래서
  - **벽은 왼쪽 · 오른쪽 반쪽으로 나눈다** (반쪽 = 45°). 반쪽의 양 끝 방향이 모두 지금 시선에서 90° 안쪽일 때만 그린다(`js cull`). 시야(가로 ±31°)는 언제나 채워진다. 무늬는 반쪽마다 200% 폭 배경을 왼/오른쪽에 맞춰 이어 붙인다.
  - **바닥 · 천장은 한 장이 카메라를 따라 돈다** (`rotateY(−yaw)`) — 언제나 카메라 앞쪽(발밑 r0 ~ 방 모서리)만 덮는다. 무늬가 방 한가운데를 중심으로 둥글어서 따라 돌아도 겉모습이 같다. (부채꼴 8 조각 + clip-path 로 나눴더니 그리는 양이 16배가 되어 프레임이 348ms 까지 늘었다 — 버렸다.)
  - 빛 웅덩이 · 창도 같은 규칙(양 끝이 90° 안쪽)으로 감춘다.
- 헤드리스 확인은 **GPU 래스터 모드**(`--use-gl=angle --use-angle=swiftshader --enable-gpu-rasterization`)로 찍는다. 기본(CPU) 모드는 큰 3D 판의 256px 타일 일부를 못 그려 사각 블록이 생기는데, 실제 브라우저에서는 생기지 않는다. 동작(이동 · 뒤로 · 초점) 검사는 기본 모드로 — GPU 흉내 모드는 너무 느려 시간 기반 검사가 밀린다.
- 카메라 = `.studio-world` 의 변환 하나. 매 프레임 `yaw` · `dolly` 를 계산해 CSS 변수로 넣는다(requestAnimationFrame). 다른 요소는 프레임마다 건드리지 않는다.
- `P`(원근 거리)와 창 크기는 화면 크기에서 정한다: 데스크톱 P ≈ 1200, 폰 ≈ 760. 방 반지름 R ≈ 1.9 P.
- 시야각(가로) 이 90° 보다 좁아서 멈춰 있을 때는 정면 벽 · 바닥 · 천장만 보이고, 옆 정거장 창은 돌 때만 시야에 들어온다.

### 5-3. 지금 화면 붙이기 (2차 — 카메라를 건드리지 않는 법)

**함정:** 변환(transform)이 걸린 조상 안에서는 `position: fixed` 가 화면이 아니라 그 조상을 기준으로 잡힌다. 카메라 화면들(비전 리허설 층 · 화상판 `#bqStage` · 통화 층)은 `body` 바로 밑에 `fixed` 로 뜬다 — 3D 트리 안에 넣으면 배치가 깨진다.

**그래서:** 기존 화면은 3D 트리에 넣지 않는다.

1. 멈춰 있을 때: 정면 창의 화면 위치(사각형)를 계산해, 기존 화면(지금처럼 `body` 의 `fixed` 층 · `#app`)을 **그 사각형에 맞춰** 2D 로 띄운다. 창이 1:1 이라 3D 창과 픽셀이 겹친다 — 사용자는 차이를 모른다.
2. 돌기 직전: 2D 화면을 숨기고 3D 창에 그 화면의 「껍데기」(제목 · 배경 · 자리표시)를 보인다 → 돌기 → 도착하면 다시 2D 화면.
3. 카메라 스트림은 정거장 ② → ③ 으로 넘어갈 때 지금처럼 넘겨받는다(`rhHandCamera`) — 그 코드는 그대로 두고, 껍데기만 돈다.

이 방식이면 카메라 · 녹화 · 정면 판단 코드는 한 줄도 바뀌지 않는다.

## 6. 접근성 · 성능

- 지금 정거장이 아닌 창은 `inert` + `aria-hidden`. 도착하면 그 창 제목으로 초점을 옮기고, 화면 읽기에 「2단계 발표로 왔어요」 를 알린다.
- 브라우저 뒤로 가기 = 이전 정거장(−90°). 정거장마다 기록을 남긴다.
- 흐림 · `filter` 를 쓰지 않는다. 그라디언트와 불투명도만. 매 프레임 바꾸는 것은 `.studio-world` 의 `transform` 과 조명 변수뿐.
- 폰: 같은 방 · 같은 회전, 창은 화면 폭 92%. 가로 스크롤 없음.
